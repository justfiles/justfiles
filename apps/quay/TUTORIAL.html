How quay's native shell works

quay turns each mini-app into a real macOS app — its own Dock icon, its own Spotlight entry — while rendering its UI in a system WKWebView with no bundled browser engine. This page walks through Phase 0: the native shell, built and verified before any backend exists. We start with one tiny Swift program and grow outward.

Background reading: DESIGN.md (the why) · PLAN.md (the slices). All code lives in native/ and launcher-ui/.

01The big picture

Phase 0 has exactly two kinds of process, and both are produced from the same compiled Swift binary:

  • The launcher (Quay.app) — a background agent with a global hotkey. Press ⌥ Space and a translucent panel appears, listing your apps.
  • A booter (Code.app, Finder.app, …) — one per mini-app. It opens a window, points a WKWebView at the app's UI, and gets out of the way. It has no app logic and no assets of its own.

Clicking an item in the launcher doesn't open a window inside the launcher — it asks macOS to launch that app's .app bundle as its own process. That single decision is what buys every mini-app a real OS identity.

02The shape of the project

Eight small files. That's the whole shell.

apps/quay/native/
  main.swift        # entry point — picks a mode and starts the app
  Booter.swift      # mode A: one mini-app window
  Launcher.swift    # mode B: the hotkey panel + JS bridge
  makeicon.swift    # draws the app icons at build time
  build.sh          # compiles + assembles the .app bundles
apps/quay/launcher-ui/
  index.html        # the launcher panel's markup + styles
  launcher.js       # the (mocked) app list + click handling

The Swift files compile into a single binary. build.sh copies that one binary into every .app it produces; the bundles differ only in their Info.plist and icon. So the first thing to understand is how one binary knows whether it should be a launcher or a booter.

03One binary, two modes

Source: native/main.swift

When the binary starts, it resolves a small Config. The key question is: do we have an app id? An app id can come from the bundle's Info.plist (the QuayAppId key), a command-line flag, or an environment variable — in that order of override. 

let raw = args.contains("--launcher")
    ? nil
    : (arg("--app") ?? env["QUAY_APP_ID"] ?? info["QuayAppId"] as? String)
let id = (raw?.isEmpty == false) ? raw : nil   // "" counts as “no id”

The presence of an id decides everything. With an id, we're a booter for that one app and we behave like a normal foreground application. Without one, we're the launcher — an LSUIElement background agent with no Dock icon. 

if let appId = config.appId {
    app.setActivationPolicy(.regular)    // real foreground app: Dock icon + menu
    delegate = BooterDelegate(appId: appId, name: config.appName, target: config.targetURL)
} else {
    app.setActivationPolicy(.accessory)  // LSUIElement: no Dock icon
    delegate = LauncherDelegate()
}
app.delegate = delegate
app.run()

setActivationPolicy is the runtime switch between “foreground app” and “background agent.” The delegate is held in a top-level constant because NSApplication.delegate is a weak reference — if nothing else retained it, it would vanish the moment app.run() started.

04The booter: a window with an identity

Source: native/Booter.swift

The booter is deliberately dumb. On launch it builds one window, drops a WKWebView into it, and loads a target. In Phase 0 there's no backend to point at, so it renders a local mock page; in Phase 1 the same code path will load http://127.0.0.1:PORT/app/<id> instead. 

let rect = NSRect(x: 0, y: 0, width: 480, height: 360)
window = NSWindow(
    contentRect: rect,
    styleMask: [.titled, .closable, .miniaturizable, .resizable],
    backing: .buffered, defer: false
)
window.title = name

webView = WKWebView(frame: rect, configuration: WKWebViewConfiguration())
window.contentView = webView

if let target {
    webView.load(URLRequest(url: target))               // Phase 1: the real UI over http
} else {
    webView.loadHTMLString(Self.mockHTML(...), baseURL: nil)  // Phase 0: a mock page
}
window.makeKeyAndOrderFront(nil)
Why this matters

WKWebView renders with the operating system's own WebKit — the same engine Safari uses — running in a separate com.apple.WebKit.WebContent process that macOS spawns for you. The app bundle ships zero browser bytes. That's the headline difference from Electron: a booter binary is ~124 KB, not ~150 MB.

The booter also installs a two-item menu (Close Window, Quit) so the standard ⌘W / ⌘Q shortcuts work and quit only this app — because each booter is its own process, ⌘Q can't take the others down with it.

Ad-hoc signing

codesign --force --sign - applies an ad-hoc signature (the - means “no identity”). Because the bundles are built locally they carry no quarantine flag, so Gatekeeper is happy — no Apple Developer account needed for local use. Notarisation is only required to distribute an app.

06The launcher: a panel you summon

Source: native/Launcher.swift

The launcher's window is an NSPanel with no title bar, floating above everything, with a clear background. The blur behind it is an NSVisualEffectView, and the actual UI is a WKWebView on top — made transparent so the vibrancy shows through. Three layers, nested: 

panel = KeyablePanel(contentRect: rect, styleMask: [.borderless], ...)
panel.level = .floating
panel.isOpaque = false
panel.backgroundColor = .clear

let blur = NSVisualEffectView(frame: rect)
blur.material = .sidebar
blur.blendingMode = .behindWindow
blur.wantsLayer = true
blur.layer?.cornerRadius = 16
blur.layer?.masksToBounds = true        // clip the web view to the rounded corners

webView = WKWebView(frame: rect, configuration: cfg)
webView.setValue(false, forKey: "drawsBackground")   // transparent → vibrancy shows through
blur.addSubview(webView)
panel.contentView = blur

let dir = Bundle.main.resourceURL!.appendingPathComponent("launcher-ui")
webView.loadFileURL(dir.appendingPathComponent("index.html"), allowingReadAccessTo: dir)

Two small but necessary details. A borderless window can't become “key” (accept keyboard focus) by default, which would break the search field — so KeyablePanel is a one-line subclass that overrides canBecomeKey to return true. And setValue(false, forKey: "drawsBackground") is the (undocumented but long-standing) way to make a WKWebView transparent so the blur underneath is visible.

In Phase 0 the UI is loaded straight off disk with loadFileURL. In Phase 1 this becomes a 127.0.0.1 URL served by the daemon — a secure context, so localStorage and ES modules work — but the rest of the panel is unchanged.

07The global hotkey

Source: native/Launcher.swift · Hotkey

The panel is summoned with ⌥ Space from anywhere, even when the launcher isn't focused. That's a system-wide hotkey, which on macOS is registered through Carbon's RegisterEventHotKey. It's old API, but it's the right tool: unlike an event tap, it needs no Accessibility permission.

The wrinkle is that the event handler you install is a plain C callback — it can't capture Swift state. So we pass a pointer to our Hotkey object through the userData channel and unwrap it on the other side. This “trampoline” from C back into Swift is the only fiddly part: 

final class Hotkey {
    private var ref: EventHotKeyRef?
    private let onPress: () -> Void

    init(keyCode: UInt32, modifiers: UInt32, onPress: @escaping () -> Void) {
        self.onPress = onPress
        var spec = EventTypeSpec(eventClass: OSType(kEventClassKeyboard),
                                 eventKind: UInt32(kEventHotKeyPressed))
        let this = Unmanaged.passUnretained(self).toOpaque()       // self → raw pointer
        InstallEventHandler(GetApplicationEventTarget(), { _, _, userData in
            Unmanaged<Hotkey>.fromOpaque(userData!)                // raw pointer → self
                .takeUnretainedValue().onPress()
            return noErr
        }, 1, &spec, this, nil)
        let hkId = EventHotKeyID(signature: 0x5155_4159 /* 'QUAY' */, id: 1)
        RegisterEventHotKey(keyCode, modifiers, hkId, GetApplicationEventTarget(), 0, &ref)
    }
}

The closure passed to InstallEventHandler captures nothing, so Swift will convert it to a C function pointer. passUnretained / takeUnretainedValue are safe here because the Hotkey lives for the whole process (the launcher delegate holds it).

08Talking to JavaScript

Source: native/Launcher.swift · launcher-ui/launcher.js

The launcher UI is web content; the launching is native. They meet through WebKit's message bridge. Two pieces wire it up. First, a WKUserScript injected at document start defines a small window.quay helper, so the page never has to know the raw postMessage plumbing: 

window.quay = {
  open: function (id) { window.webkit.messageHandlers.quay.postMessage({ action: 'open', id: id }) },
  hide: function () { window.webkit.messageHandlers.quay.postMessage({ action: 'hide' }) }
}

Second, the Swift side registers as a WKScriptMessageHandler for the channel named "quay" and dispatches on the message: 

func userContentController(_: WKUserContentController, didReceive message: WKScriptMessage) {
    guard let body = message.body as? [String: Any],
          let action = body["action"] as? String else { return }
    switch action {
    case "open":
        if let id = body["id"] as? String { hide(); openMiniApp(id) }
    case "hide":
        hide()
    default: break
    }
}

09Launch by identity, not window

Source: native/Launcher.swift · openMiniApp

Here's the heart of the whole design. When you pick an app, the launcher does not create a window. It asks NSWorkspace to launch the corresponding .app bundle by its bundle identifier. LaunchServices finds it (wherever it's registered) and starts it as its own process — which is exactly why it gets its own Dock icon and Cmd-Tab entry. 

private func openMiniApp(_ id: String) {
    let bundleId = "app.justfiles.quay.app.\(id)"
    if let url = NSWorkspace.shared.urlForApplication(withBundleIdentifier: bundleId) {
        NSWorkspace.shared.openApplication(at: url, configuration: .init())
        return
    }
    // dev fallback: open the generated bundle directly if it isn't registered yet
    // ...
}
The reframe

Electron gives you windows; it can't give a per-window Dock identity. quay launches bundles. “A Dock icon needs a process” is the constraint, so quay makes each mini-app a process — a tiny Swift booter, not a Chromium instance.

10The launcher UI

Source: launcher-ui/launcher.js · launcher-ui/index.html

The web side is intentionally tiny and, for Phase 0, the app list is mocked right in the file. In Phase 1 this same array gets replaced by a list fetched from quayd over a socket — but the rendering and click handling don't change. 

const apps = [
    { id: 'code', name: 'Code', glyph: 'C' },
    { id: 'finder', name: 'Finder', glyph: 'F' },
    { id: 'paint', name: 'Paint', glyph: 'P' }
]

function launch(id) {
    if (window.quay) window.quay.open(id)   // the bridge from §8
}

function render(filter = '') {
    const q = filter.trim().toLowerCase()
    const items = apps.filter((a) => a.name.toLowerCase().includes(q))
    grid.replaceChildren(...items.map((a) => {
        const li = document.createElement('li')
        li.addEventListener('click', () => launch(a.id))
        // …build the tile (glyph + label)…
        return li
    }))
}

The search box filters the list as you type; Enter launches the first match; Esc calls window.quay.hide(). Tiles are built with document.createElement and textContent rather than innerHTML — a small habit that keeps the door shut on injection once the list comes from real data.

11The build script

Source: native/build.sh

No Xcode project, no xcodebuild — just swiftc and a shell script (Command Line Tools are enough). It compiles the shared binary once, then assembles a bundle around it. The first argument selects what to build: 

# compile the one binary that powers both modes
swiftc -O -swift-version 5 main.swift Booter.swift Launcher.swift -o "$BIN"

case "${1:-}" in
    --launcher) build_launcher ;;          # Quay.app  (LSUIElement, ships launcher-ui)
    --apps)     build_mini_apps ;;         # Code/Finder/Paint.app into ~/Applications/Quay Apps/
    *)          build_booter "$1" ;;       # e.g. ./build.sh Code  →  ./Code.app
esac

Assembling a bundle is just copying files into the right folders and signing:

cp "$BIN" "$app/Contents/MacOS/$name"            # the shared binary
emit_plist "$name" "$bundle_id" "$quay_id" "$lsui" > "$app/Contents/Info.plist"
make_icon "$app" "$letter"                       # makeicon.swift → AppIcon.icns
codesign --force --sign - "$app"                 # ad-hoc

For the mini-apps, the script also runs lsregister so that LaunchServices — and therefore Spotlight, and the launcher's open-by-bundle-id call — can find them: 

.../LaunchServices.framework/Support/lsregister -f "$app"

The icons themselves are drawn programmatically by makeicon.swift: a rounded square plus the app's first letter, with the colour derived from the letter so Code, Finder and Paint look distinct. It renders PNGs that iconutil packs into an .icns.

12A bug we hit (and what it taught us)

Symptom

The launcher process ran fine, but pressing the hotkey was the only way to see the panel — an early version tried to also show it on launch, and that silently did nothing.

The cause is a real macOS rule worth remembering: an LSUIElement (background) app cannot take foreground — and therefore cannot show a window — at launch time. macOS only grants a background agent the right to come forward in response to a user action. A global hotkey press counts; “the app just started” does not.

So the fix wasn't code — it was deleting the auto-show. The panel is summoned by the hotkey, which is precisely the Spotlight-like model the design intended. The show() path is identical either way; only the trigger differs.

Debugging note

Confirming this was harder than usual: a GUI app launched via open runs outside the shell's sandbox, so files and NSLog output it produced were invisible to the terminal. The reliable signals turned out to be CGWindowListCopyWindowInfo (does an on-screen window exist, and where?) and capturing a specific window by its id with screencapture -l<id>.

13Recap & try it

The whole shell, in one breath:

  1. One Swift binary; QuayAppId decides booter vs. launcher (§3).
  2. A booter is a window hosting a system WKWebView — no bundled engine (§4).
  3. A .app is a folder; identity lives in Info.plist (§5).
  4. The launcher is a vibrancy panel summoned by a Carbon global hotkey (§6–7).
  5. Web → native goes over WebKit's message bridge; authority stays native (§8).
  6. Picking an app launches its bundle by id — its own process, its own identity (§9).

Build it and poke at it:

cd apps/quay/native

./build.sh Code        # → ./Code.app — open it: a window with its own Dock icon
open ./Code.app

./build.sh --launcher  # → ./Quay.app — the background launcher
./build.sh --apps      # → mock Code/Finder/Paint into ~/Applications/Quay Apps/
open ./Quay.app        # no Dock icon appears; press ⌥Space, then click Code

Verify it's really system WebKit and not a bundled engine: 

otool -L Code.app/Contents/MacOS/Code | grep WebKit
du -sh Code.app        # ~200 KB, most of it the icon
