apps/desktop · design & plan

A native macOS shell for the JustFiles app system

Turn apps/desktop into a Raycast-style launcher that runs the same @justfiles/app-* apps frieren runs today — but in a real macOS process, on a Volume backed by the local filesystem, with the pi agent running in the background and full access to live app state.

1 · The core reframe

frieren is split across two kernels over a synced volume: a browser kernel (your tab) and a server kernel (a Cloudflare Durable Object). The network is the boundary — a /fs HTTP sync channel, a Cap'n Web WebSocket for capabilities, and a third WebSocket for the agent. The agent lives server-side and its writes reach your open windows only after they sync down and a file-watch fires.

The desktop app has no remote server. That lets us collapse the split into one local process: a single kernel, a single Volume backed by the real macOS filesystem, and the agent running in-process next to it. Everything that was a network hop in frieren becomes either an in-process function call or an Electron main ↔ renderer IPC message. The hard distributed-systems machinery frieren needs (sync, watch-driven coherence, Cap'n Web RPC) simply isn't needed here.

The thesis in one line
Keep @justfiles/app, @justfiles/fs, the app bundles, the GUI shim and the agent tools exactly as they are. Write three small adapters: a Node sandbox (worker_threads), an IPC transport for GUIs, and an app:// protocol for assets. Point the Volume at a real folder. Run the agent in the main process. Done.

2 · How frieren works today

The system is built from a few sharp, host-agnostic layers. The whole point of the design is that a host supplies three seams — a Volume, a GetSandbox, and a Capabilities implementation — and the kernel does the rest. frieren supplies those seams twice (once in the browser, once on the server). Desktop will supply them once.

LayerPackage / fileWhat it is
Volume @justfiles/fs · volume.ts POSIX-ish path API (readFile, writeFile, readdir, rename, watch, scan, xattrs, symlinks) over a pluggable Storage K/V backend. chroot() scopes a sub-tree.
Storage backends storage.mem · storage.idb · storage.fs memory, IndexedDB, and nativeStorage(root) — already backed by the real OS filesystem. synced() wraps a local backend for remote replication.
Kernel @justfiles/app · kernel.ts kernel({ fs, sandbox, capabilities }). Owns the /applications bundle store, the /state/<id>.json state store, a per-app serialized dispatch queue, commands, procedures, and capability-fed subscriptions. Emits app.update events.
Sandbox seam GetSandbox Runs an app's compiled app.js in an isolate. frieren has two: browserSandbox() (a Web Worker per bundle, sandbox.worker.ts) and workerSandbox() (a Cloudflare Worker Loader isolate, kernel.sandbox.ts).
Capability seam capabilities/types.ts One interface: { invoke(call), subscribe(call, emit) }. The kernel attaches the app's declared, trusted scopes to every call. Composed by capabilityRegistry() from local units (volumeCapability, aiCapability, devkitCapability) and/or a remote proxy.
App + GUI defineApp · react.ts · vite.ts An app is a headless reducer (app.ts) plus a browser GUI (gui.tsx). The kernelHost() Vite plugin builds manifest.json, app.js, gui.js and a self-contained bundle.js.
Agent worker/frieren.runtime.ts · tools.ts · bash/commands/app.ts @mariozechner/pi-agent-core with tools over the Volume (read/write/ls/mkdir/rm), web fetch/search, and a bash shell whose app command drives an AppController → the kernel (list / launch / inspect / state / run).

3 · Desktop process model

Electron gives us exactly two kinds of process: one main process (full Node.js) and many renderer processes (sandboxed Chromium). That maps cleanly onto the split we want:

  • Main process = the host. It owns everything that needs Node or must be singular: the Volume (native FS), the one kernel, the capability registry, and the pi agent. It also manages windows, registers the app:// protocol, and routes IPC. This is the background agent the PLAN already builds (no Dock icon via LSUIElement).
  • Renderer = a GUI. Each app opens in its own BrowserWindow that renders that app's gui.js — the same React/GUI-shim stack frieren mounts in a tab. The renderer never touches Node, the FS, or the kernel directly; it reaches the host through a tiny preload bridge.
  • worker_threads = sandboxes. The kernel's GetSandbox runs each app's app.js in a Node worker_thread — a direct port of frieren's Web-Worker sandbox. App reducer code never runs on the main thread (isolation + no event-loop blocking).
main process (Node) renderer (Chromium) worker_threads real filesystem
Decision · where the host lives
Put kernel + Volume + capabilities + agent all in the main process for v1 — it is the simplest possible wiring (direct function calls, one process to reason about) and honours “keep code minimal”. Only the sandboxes must be off-thread, and they go to worker_threads. If the agent's CPU work (compaction, streaming) ever janks window management, move the whole host bundle into a single utilityProcess with main as a pure router — the internal seams don't change, only where they're instantiated.

4 · The Volume — the real filesystem

This is the part that needs almost no new code. @justfiles/fs already ships nativeStorage(root) — a Storage backend whose inodes are OS inodes and whose operations are node:fs/promises calls. Wrapping it in volume() yields a full Volume rooted at a real directory: 

// main process — the only filesystem wiring the desktop needs
import { volume } from '@justfiles/fs'
import { nativeStorage } from '@justfiles/fs/storage/fs'

const root = app.getPath('userData') + '/volume'   // a real macOS folder
const fs = volume(await nativeStorage(root))         // a Volume over real files

Every path the kernel and apps already use becomes a real file on disk. All the goodies from frieren are now things you can see in Finder:

~/Library/Application Support/justfiles/volume/ ├─ applications/ # installed app bundles (one dir per app id) │ ├─ app.justfiles.counter/ # manifest.json · app.js · gui.js · icon │ ├─ app.frieren.finder/ │ └─ app.justfiles.code/ ├─ state/ # live per-app state, one JSON each │ ├─ app.justfiles.counter.json │ └─ app.justfiles.code.json ├─ data/ # per-app private data (chroot'd /data/<id>) │ └─ app.justfiles.code/projects/<slug>/src/... # code projects └─ system/ # the agent's brain — real markdown ├─ soul.md · MEMORY.md ├─ profiles/user.md ├─ memory/daily/2026-06-10.md ├─ agents/main/sessions/*.jsonl └─ os-state.json # focused app / window layout
Reused unchanged
nativeStorage, volume(), chroot(), the kernel's /applications + /state + /data layout, the agent's /system memory layout, and the volumeCapability scope policy (app → /data/<id>; system → root for allow-listed apps).
New for desktop (small)
Choosing the root (app.getPath('userData')) and a one-time built-in seed (§8). Optionally: feed an OS-level fs.watch/chokidar into nativeStorage.caps.subscribe so files a user edits outside the app (in Finder, in their editor) also fire volume.watch — that makes Finder.app and the code editor reflect real external edits. Pure enhancement; not required for v1.

Note on volume.watch: today it only fires for writes that pass through the storage layer (which is enough for app↔agent coherence, since those go through the kernel). The OS-watch hook above is what extends it to changes made by other macOS programs.

5 · The app system

One kernel in main, one Volume, one capability registry. An app opens in its own window. Three adapters make the existing pieces fit the Electron boundary.

5.1 · The Node sandbox (nodeSandbox)

The kernel asks its GetSandbox to execute app.js. frieren's browserSandbox() spins up a Web Worker, blob-imports the bundle, and bridges procedure host-calls (dispatch / settled / invoke) back over postMessage. The Node equivalent is a near-line-for-line port to node:worker_threads:

  • One worker per bundle, keyed by the SHA-256 of the code (content-addressed reuse — identical to today).
  • The worker imports app.js via a data: URL (esbuild emits self-contained ESM, so defineApp and friends are already inlined — only React is externalised, and app.js never imports React).
  • The same five message kinds (initialState, dispatch, actions, capabilities, subscriptions, runProcedure) and the same host-call reply channel as sandbox.worker.ts — only the transport primitive changes (worker.postMessage vs the DOM Worker).
Decision · isolation mechanism
worker_threads is the right call: it mirrors the existing Web-Worker model exactly, keeps app code off the UI thread, survives an app crash without taking the host down, and needs no native deps. (A vm/SES in-process isolate is lighter but offers weaker isolation and would block main; a utilityProcess per app is heavier than needed. Pick worker_threads.)

5.2 · Serving the bundle: the app:// protocol

A GUI window needs to load gui.js and any app assets. In frieren the server exposes them at /api/apps/:appId/* (see frieren.app.ts · asset()). The desktop analogue is a custom scheme registered in main with protocol.handle: 

// main — registered once, before app windows open
protocol.handle('app', (req) => {
  const { host: appId, pathname } = new URL(req.url)   // app://<id>/gui.js
  const installed = await kernel.app(appId)            // reads the Volume bundle
  const bytes = await installed.read(safeBundlePath(pathname.slice(1)))
  return new Response(bytes, { headers: { 'content-type': mimeFor(pathname) } })
})

Registered as a standard, secure scheme so each app window gets a real, isolated origin (app://<id>), ES-module imports and fetch work, and a shared-React importmap resolves the bare react imports in gui.js to one vendored module — the same shared-runtime discipline the package README mandates. This replaces the network asset route with a local protocol; the bytes come straight off the Volume.

5.3 · The GUI transport (IPC instead of in-thread)

frieren's host.ts mounts a GUI with a Transport = { invoke(message), subscribe(onState) } and the reactGui shim wires it to the app's typed client. We keep reactGui and the stage/mount lifecycle unchanged; we only swap what the Transport calls:

Transport opfrieren (browser kernel, same thread)desktop (renderer → main)
invoke(msg)kernel.dispatch(id, msg) directlyipcRenderer.invoke('kernel:dispatch', id, msg)
subscribe(onState)local kernel.subscribe eventsmain webContents.send('app.update', …) for windows showing id
initial snapshotkernel.state(id)ipcRenderer.invoke('kernel:state', id)
load gui.jsread bytes from Volume, blob-importimport('app://<id>/gui.js')

The preload script exposes exactly this surface via contextBridge — a handful of methods, nothing else. The renderer stays fully sandboxed (no Node, no FS).

5.4 · The launcher and the catalog

The launcher (already built per PLAN.md slices 1–3) stops using its hardcoded APPS array and instead asks the host: ipcRenderer.invoke('kernel:list') → kernel.list() returns the installed manifests (id, name, icon). Picking one sends launcher:open-app <id>, and main opens a GUI window pointed at app://<id>/. When the catalog changes (an install or uninstall), main pushes catalog:changed and the launcher re-lists — the mechanism that makes a freshly built app “show up in the list.”

6 · The agent

The agent is @mariozechner/pi-agent-core (Node ≥ 20 — runs natively in Electron's main process). The runtime (frieren.runtime.ts), the tools (tools.ts), the bash shell and its app command (bash/commands/app.ts), and the AppController interface depend only on a Volume and a Kernel — and have zero Cloudflare/DO coupling. So they are lifted out of frieren into a new @justfiles/agent package (§11 · R3), which the desktop main process and the frieren DO both import. Desktop then just hands them the one kernel and the native Volume it already has in main.

6.1 · Same access to app state and tools

In frieren the AppController is backed by the server kernel and its launch/open/close only broadcast intent to the browser, which owns the windows. On desktop the controller is backed by the same single kernel the GUIs use, and open/close directly drive native windows: 

// main — the desktop AppController, ~20 lines over the existing interface
const controller: AppController = {
  list:    () => kernel.list(),
  inspect: (id) => ({ ...manifest, state: kernel.state(id), actions: kernel.actions(id) }),
  state:   (id) => kernel.state(id),
  run:     (id, action, params) => kernel.dispatch(id, { type: action, params, actor: 'agent' }),
  launch:  (id) => { openAppWindow(id); return inspect(id) },   // opens a real window
  close:   (id) => closeAppWindow(id ?? focusedAppId()),
  current: () => inspect(focusedAppId())                         // from the window manager
}
createAppCommand(controller)   // unchanged — the agent's `app` bash command

So the agent can app list, app launch <id>, app inspect, app state, app actions, and app run <action> key=value against the live apps — plus read/write the Volume with its fs tools (memory, profiles, project sources, anything). The current app comes straight from the window manager (focused BrowserWindow → its app id), rather than from parsing os-state.json.

6.2 · Coherence comes for free

This is where the single-kernel model pays off most. In frieren, an agent dispatch hits the server kernel; its app.update can't reach the browser directly, so the server nudges the caps socket (dirty), the browser flushes the volume sync, and an open window only re-renders when a volume.watch('/state/<id>.json') fires. On desktop the agent dispatches into the same kernel the windows subscribe to, so its app.update fans out to every window showing that app immediately — no sync, no watch, no proxy.

6.3 · The agent UI boundary

frieren's agent UI (AgentProvider, MessagesPanel) is deliberately transport-agnostic: it drives an AgentClient built over a SocketLike injected via createSocket (os/client.ts). On desktop we inject an IPC-backed SocketLike — send → ipcRenderer.send('agent:prompt', …), incoming onmessage fed by webContents.send('agent:event', …). The React layer is reused verbatim; only the socket shim is new. (A dedicated MessageChannelMain port is the clean choice for the high-rate event stream.)

Extracted, then reused
The pi-agent-core runtime, compaction, sessions, the fs/fetch/search/takeNote tools, the bash registry, and createAppCommand + the AppController contract move into @justfiles/agent (§11 · R3) — frieren and desktop consume the same package. The agent React UI is reused via its SocketLike seam (its client half can move to @justfiles/agent/client so the WS and IPC hosts share it).

7 · Capabilities

The capability seam is one interface — { invoke, subscribe } — composed by capabilityRegistry(). On desktop everything runs in-process, so the registry is the whole story; there is no Cap'n Web proxy and no _caps socket at all: 

// main — one registry, all local
const capabilities = capabilityRegistry({
  volume:       volumeCapability(fs, { systemAllowlist }),  // @justfiles/app (§11 · R1)
  ai:           aiCapability(text),                         // calls the LLM directly from Node
  integrations: integrationsCapability(reg),                // optional; talks to providers directly
  devkit:       devkitCapability(fs, kernel, preview),      // thin shell over @justfiles/app/devkit (§11 · R2)
})
const kernel = kernel({ fs, sandbox: nodeSandbox(), capabilities })

The trust model is preserved exactly: apps declare capabilities in defineApp; the kernel attaches the declared, trusted scopes to each CapabilityCall (the worker_thread isolate never supplies its own). volumeCapability's scope rules are unchanged — app → /data/<id> chroot, an explicit /prefix → that subtree, system → the root only for an allow-listed app. Its one frieren-specific value (the hardcoded ['app.frieren.finder'] system allow-list) becomes a parameter when it moves to @justfiles/app (§11 · R1), so each host passes its own.

Capabilityfrierendesktop
volumelocal on the browser kernellocal on the one kernel (native FS)
devkitlocal, esbuild-wasm, allow-listedlocal, native esbuild, allow-listed
ai / integrationsproxied to the server over Cap'n Web WSlocal — main calls the network directly

8 · app-code — build and install to the Volume

packages/app-code is itself just an app. Its “Build & Install” power comes from the devkit capability, which: reads a project's src/* off the Volume, compiles app.ts/gui.tsx with esbuild, and either mounts a live preview or installs a finished bundle into /applications. On desktop this maps directly, with one wrinkle (the preview).

8.1 · Seeding the built-ins

The same reconcileBuiltins(kernel, fs, catalog, read) — moved out of frieren into @justfiles/app (§11 · R1) — seeds the desktop Volume on first run; only read differs, resolving bytes from the packaged app resources instead of an HTTP asset binding. Each packages/app-* already builds a self-contained bundle.js (BuiltinBundle = { id, version, manifest, files }) via kernelHost(); main installs them with kernel.install(appBundleFromMemory(...)). After seeding, the launcher's kernel.list() shows the built-ins.

8.2 · Compile + install (the easy 90%)

install and pack are pure data transforms — read sources, run esbuild, write a bundle — and they extract wholesale into @justfiles/app/devkit as installDraft / packDraft (§11 · R2). The desktop host writes no build logic of its own: it supplies a native-esbuild toolchain (the engine is injected; the stdlib comes from the same extracted buildRuntime()) and calls those functions. installDraft calls kernel.install, which writes /applications/<id> to real disk, then fires its onInstalled hook → main emits catalog:changed and the launcher re-lists. No code change to app-code's reducer — it already invokes devkit.install.

8.3 · The live preview (the one wrinkle)

In frieren, devkit.run mounts the freshly compiled draft into the code app's own DOM at a [data-preview-slot] — trivial because the browser kernel, the host, and esbuild all live on one thread. On desktop the kernel is in main and the code app is a separate renderer, so the preview can't be a same-thread appendChild. Two clean options:

OptionHowTrade-off
A · embedded WebContentsView (recommended) main compiles → installs preview.<slug> into a scratch-scoped kernel → attaches a WebContentsView loading app://preview.<slug>/ over the slot rect the code window reports (the same “report your rect” trick the launcher already uses for its height). True process/origin isolation of the preview; reuses the whole app-window path. A little geometry plumbing to keep the view aligned with the slot on resize/scroll.
B · preview in the code renderer Run a small browser-side kernel + Web-Worker sandbox inside the code window just for the preview (frieren's exact client path), with its volume capability proxied to main. Closest to frieren's code; but reintroduces a second kernel + a proxy for one feature. Heavier than A.
Decision
Ship compile + install + pack first (no UI embedding — the agent and the GUI can install apps immediately) — and those come for free from @justfiles/app/devkit (§11 · R2). Add the WebContentsView preview (A) as a follow-up slice; the preview mount is precisely the seam §11 deliberately leaves per-host, so it's the only part of the whole design that isn't a near-verbatim reuse.

11 · Extract the platform layer first

Sections 4–8 keep saying “reused.” For that to be literal rather than copy-paste, the host-agnostic code has to leave frieren and move into shared packages the desktop imports. None of it is coupled to Cloudflare, the Durable Object, the DOM, or auth — verified: zero cloudflare: / env. imports across the agent and shared/ sets — so this is a mechanical refactor done inside the monorepo with frieren as the proving ground, its existing tests the guardrail. Doing it before any desktop code means the desktop host is mostly assembly.

11.1 · Promote the seam implementations into packages/app

packages/app already ships the capability contracts; the host-agnostic implementations are stranded in frieren/shared (already consumed by both of frieren's hosts, client and server — desktop is just a third). Move each next to its contract:

MoveFrom → ToDe-frieren
volumeCapability + resolveVolume shared/volume.capability.ts → @justfiles/app/capabilities/volume/host the hardcoded SYSTEM_SCOPE_ALLOWLIST becomes a parameter the host passes
reconcileBuiltins + Catalog types shared/appstore.ts → @justfiles/app/builtins none — the read() byte source is already host-supplied
bundleFromZip shared/app-bundle.ts → @justfiles/app none (fflate dep)

11.2 · The devkit build pipeline → @justfiles/app/devkit

This is the highest-leverage extraction, and it is not forced — the split between the generic build pipeline and the host's preview presentation is sharp. Method by method, roughly two-thirds is generic:

devkit methodgeneric (Volume + injected esbuild + Kernel)host-specific
pack100% — read project, compile, assemble manifest, zip—
install~90% — read, compile, icon, collision-check, kernel.installthe kernel instance + an onInstalled callback
run~60% — read, compile, diagnostics, build the bundlemount the preview (DOM stage vs WebContentsView)
stop/menu/selectMenuthe MenuView mappingteardown + the live-menu bridge
project I/O · compile · buildRuntime100% — pure Volume + Node esbuild—
Precedent
packages/app/vite.ts (the kernelHost plugin, exported as @justfiles/app/vite) already imports esbuild and node:fs as a Node-only host build subpath. A @justfiles/app/devkit subpath is the same category — Node-only, esbuild-using, never pulled into the kernel/sandbox graph. The esbuild import in compile is type-only (the engine is injected).

The extracted surface — engine and I/O injected, presentation left to the host:

// @justfiles/app/devkit  — Node host subpath (peer of @justfiles/app/vite)
export type Toolchain = { build: BuildFn; runtime: Record<string, string> }

export function buildRuntime(opts?): Promise<Record<string, string>>          // the stdlib bundler (Node esbuild)
export function compile(files, entries, build, runtime): Promise<CompileResult>
export function buildDraft(data, slug, tc): Promise<{ manifest; app?; gui?; icon?; diagnostics }>
export function installDraft(fs, appId, slug, kernel, tc, hooks?): Promise<{ id }>
export function packDraft(data, slug, tc): Promise<{ zip }>

…which collapses each host's devkit to thin wiring plus its own preview object:

// desktop main — the whole host-side devkit
const toolchain = async () => ({ build: esbuild, runtime: await buildRuntime() })   // native esbuild
export const devkitCapability = (fs, kernel, preview) => implementCapability(devkit, {
  install: (ctx, { slug }) => installDraft(fs, ctx.appId, slug, kernel, await toolchain(), { onInstalled: preview.notifyCatalog }),
  pack:    (ctx, { slug }) => packDraft(chroot(fs, `/data/${ctx.appId}`), slug, await toolchain()),
  run:     (ctx, input)    => preview.run(ctx.appId, input, await buildDraft(/* … */)),  // host mounts
  stop:    (ctx, { previewId }) => preview.stop(previewId),
  menu:    (ctx, { previewId }) => preview.menu(previewId),
  selectMenu: (ctx, a)     => preview.selectMenu(a),
})
The line not to cross
The preview object (mount / teardown / menu) stays per-host and should — a frieren [data-preview-slot] and a desktop WebContentsView rect have nothing in common, so abstracting the mount would be the exact over-engineering CLAUDE.md warns against. Everything above the mount extracts; the mount does not.

11.3 · The agent → a new @justfiles/agent package

The whole runtime loop is the reusable unit, not just the tools. A new sibling package bundles the runtime, the fs/fetch/search/takeNote tools, the bash registry + commands, and createAppCommand + the AppController interface (the agent↔kernel bridge). The host injects the model and an AppController; the persona/memory are already data on the Volume (/system/soul.md, …). 

// @justfiles/agent  — depends on @justfiles/app + @justfiles/fs + pi-agent-core/pi-ai
const agent = await createAgentRuntime({
  volume, llm: { model, apiKey },   // host picks the model — no OpenAI baked in
  appController,                    // host-supplied: desktop opens real windows; frieren broadcasts
})
Why a new package, not packages/app
The agent pulls pi-agent-core + pi-ai (heavy LLM deps). packages/app gets externalised into worker isolates and must stay lean — those deps cannot leak in. The agent is a consumer of the kernel, not part of it, so @justfiles/agent → @justfiles/app is the correct one-directional boundary.

11.4 · Optional — a shared sandbox protocol

browserSandbox, workerSandbox, and the desktop nodeSandbox all re-implement the same worker message protocol (initialState / dispatch / actions / capabilities / subscriptions / runProcedure + the dispatch/settled/invoke host-call bridge) — only the transport differs. A sandboxProtocol(send, recv) helper in packages/app makes nodeSandbox ~30 lines of worker_threads glue and dedupes frieren's two existing adapters. Nice-to-have, lower priority than R1–R3.

12 · Implementation slices

Slices 1–4 (the shell) are done per PLAN.md. The rest splits into two phases. Phase A extracts the reusable platform layer (§11) into shared packages — entirely inside the monorepo, with frieren's tests as the guardrail and no desktop code yet. Phase B then assembles the desktop host from those packages. Every slice ends with pnpm format && pnpm typecheck && pnpm lint:fix && pnpm test.

8Capabilities in-process — capabilityRegistry({ volume: volumeCapability(fs, { systemAllowlist }) }) (R1); ai/integrations if keys present. Finder and Paint (which use volume) work end-to-end against real files.
9Agent in main — instantiate @justfiles/agent (R3) with a desktop AppController (real windows) + an IPC SocketLike; agent UI in the launcher (or its own window). Agent can app list/launch/run, edit memory, and an open Counter updates live when the agent increments it.
10app-code build & install — thin desktop devkit over @justfiles/app/devkit (R2): installDraft/packDraft with a native-esbuild toolchain; install → /applications → catalog:changed → launcher re-lists. Author a project in app-code, click Install, and it appears in the launcher with no code change.
11Live preview — the only bespoke devkit code: a WebContentsView preview over the code window's slot, wiring run/stop/menu. Edits in app-code re-render the embedded preview, mirroring frieren.

13 · Open questions & future work

  • Sync back to frieren (next stage). The hooks exist: wrap nativeStorage with synced({ local, remote: apiStorage(...) }). But synced needs the local backend to implement the sync caps (deltaUpdates, applyBatch, a stable cursor) that nativeStorage doesn't yet have. Designing those on top of real inodes (which can change across moves) is the substantive piece of the “sync with frieren” stage.
  • External edits. Do we want Finder.app / the code editor to reflect files a user changes in macOS Finder or another editor? If so, the OS fs.watch → caps.subscribe hook in §4 is required (and we should debounce + reconcile the lazy pathMap on external moves).
  • Agent placement. Start in main; promote to a utilityProcess only if streaming or compaction janks window management. Decide the trigger (e.g. measured main-thread frame stalls).
  • Preview isolation vs. fidelity. Confirm the WebContentsView approach (A) over the in-renderer kernel (B); validate slot geometry on resize, multi-display, and HiDPI.
  • Signing / notarisation / auto-update. Tracked in PLAN.md as deferred; unchanged by this design.
