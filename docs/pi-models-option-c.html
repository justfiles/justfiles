accounts → connections

Delete the generic broker; keep one thin shared credential. Capability availability is derived from the connection's granted scopes — not stored in a table — matching how Composio, Arcade, MCP and pi-ai all do it. The only persisted selection is the single active AI. And Option C (pi Models) stops being a special case.

The shape. One persisted per-account type — a Connection = { id, kind, creds, scopes }. "Which capability does it back?" is a pure function of kind + granted scopes (backs()), computed at call time — there is no persisted capability→connection map. The one thing that can't be derived (which connection + model is the single active AI) is a single pointer, activeAi. That's it.

This drops the earlier Wiring type entirely, on the strength of the research below: the platforms whose whole job is agent-to-account auth never persist a wiring table — they scope credentials to a provider and derive capability from scopes/status. Result: 1 persisted type + 1 selection pointer, no Provider.mint, no generic resolver, no hand-rolled OAuth, no /compat.

1. How the field does it (research)

Before hardening a Wiring type, we checked the systems whose entire product is “let an agent act on a user’s internet accounts”, plus the emerging standard and our own dependency:

SystemPersisted unitHow “what can it do” is decidedWiring table?
ComposioConnected Account {toolkit, creds, status, scopes} + a code-level Auth ConfigThe connection belongs to a toolkit (Gmail → Gmail tools); enable/disable is a status field on the connection (ACTIVE/INACTIVE)no
ArcadeUser token per providerEach tool declares required scopes; availability is derived from the token’s granted scopes (prompt if missing)no
MCP (2025-06 auth)Token bound per resource/server (RFC 8707); STDIO reads creds from envToken ⇄ the resource that uses itno
pi-ai (our dep)CredentialStore keyed by providerId, one credential per provider, locked auto-refreshProvider owns its capability; “which model” is a separate selectionno

The pattern is unanimous:

  • One persisted unit — the connection ({provider, creds, scopes, status}), keyed per provider.
  • Capability is derived from the provider + granted scopes (a pure function / static “auth config”), never a per-user capability→connection table.
  • Enable/disable is a field/scope on the connection, not a join.
  • Refresh belongs to the credential layer and is automatic.
  • Selection, where it exists, is a single minimal pointer (pi: which model; Composio: user+toolkit → account).
Verdict: a standalone persisted Wiring map is a moving part none of the best-in-class have. We collapse it — derive email/calendar from scopes, and keep the one irreducible bit (the single active AI) as a pointer.

3. Why not delete “Account” outright

If each capability owned its auth with nothing shared, the shared-credential fact resurfaces one of three ways — none simpler:

  • Double sign-in. Google once for mail, again for calendar → two refresh tokens for one identity. A recurring correctness + support cost.
  • “Google is a capability with sub-capabilities.” That’s the account renamed, plus a heavier concept (hierarchy), and it breaks on diamonds (iCloud also provides calendar).
  • A shared thing under another name. You’ve renamed the account.

So we keep the constraint as the thinnest possible record — a Connection — and derive everything else.

4. The model: Connection + derived capabilities

Connection pure identity + creds + granted scopes. (pi's CredentialStore is a *view* of these.) │ │ backs(connection, capability) — a PURE FUNCTION of kind + scopes (static "auth config"). No storage. ▼ email ── backs(c,'email') = google + gmail scope ─▶ compose with gmail client (fan-out) calendar ─ backs(c,'calendar')= google+cal scope | icloud ─▶ compose with gmail/caldav (fan-out) ai ── activeAi.connectionId === c.id (single pointer) ─▶ compose with pi Models (single)

No provider registry, no mint map, no generic resolver, and — the change from the first draft — no persisted wiring. A connection’s scopes are the source of truth for email/calendar; the single active-AI pointer is the source of truth for ai.

A. Storage — Account → Connection + activeAi

before — accounts/store.ts (one record does everything)
interface Account {
  accountId; providerId
  creds: Creds                                   // identity/auth …
  enabled: Partial<Record<CapabilityId, unknown>>   // … + which caps + per-cap config …
  scopes?: string[]                              // … + oauth grants
}
after — connection.ts + provider-caps.ts (code) + active-ai.ts
// The only per-account persisted type.
interface Connection { id: string; kind: string; creds: Creds; scopes?: string[] }

// Static "auth config" — CODE, not per-user state (à la a Composio Auth Config):
const PROVIDER_CAPS = {
  google:  [{ capability: 'email', scope: GMAIL_SCOPE }, { capability: 'calendar', scope: CAL_SCOPE }],
  icloud:  [{ capability: 'calendar' }],       // form provider — kind implies it
  chatgpt: [{ capability: 'ai' }],
}
const backs = (c: Connection, cap) =>                  // pure; no storage
  (PROVIDER_CAPS[c.kind] ?? []).some(x => x.capability === cap && (!x.scope || c.scopes?.includes(x.scope)))

// The one irreducible selection (ai is single-active): a pointer, not a table.
type ActiveAi = { connectionId: string; model?: string } | null
Credential lane unchanged. Connection.creds keeps the single encryptable field + secretCodec (default identity), one JSON per connection under /system/connections. activeAi is one small file. This is a field/shape migration, not a new storage substrate.

B. The broker dies; hosts derive

Delete Provider, the mint map, resolveTargets/fanOut/resolveImpl, describe, resolveAiAccount. Each host is a plain module; the fan-out that used to be generic is ~5 lines that filter connections by backs().

before — accounts/host.ts (generic broker, ~120 lines)

  mint: Partial<{ email(creds); calendar(creds); ai(creds, config) }>
  describe?: Partial<Record<CapabilityId, (c)=>unknown>> }

async function resolveTargets(cap, id, providers, accounts) { /* … */ }
async function fanOut(cap, id, providers, accounts, call)   { /* … */ }

const emailHost = (providers, accounts) => implementCapability(email, {
  listUnread: (_c,i) => fanOut('email', i.accountId, providers, accounts, x=>x.listUnread(i)),
  /* … routed through the mint map */ })
after — email/host.ts (derive with backs(), compose with the client)
import { createGmailEmail, authedFetch, googleClient } from './google.ts'
import { backs } from './provider-caps.ts'

function emailHost(connections: ConnectionStore) {
  const targets = async () =>
    (await connections.list()).filter(c => backs(c, 'email'))   // derived; no storage
  const client = (c) => createGmailEmail(authedFetch(c.creds, googleClient()))

  return implementCapability(email, {
    listUnread: async (_c, i) => (await Promise.all(
      (await targets()).map(async c =>
        (await client(c).listUnread(i)).map(r => ({ ...r, accountId: c.id }))))).flat(),
    readDetail: async (_c, i) => client((await connections.get(i.accountId!))!).readDetail(i),
    markRead:   async (_c, i) => client((await connections.get(i.accountId!))!).markRead(i),
  })
}

Calendar is the same shape (with iCloud’s backs(c,'calendar') true by kind). The Gmail/CalDAV client code is unchanged — imported directly instead of reached through a mint map.

C. The ai host = compose with pi Models

With the broker gone, the ai host composes with pi. The single active-AI pointer selects the connection; a tiny CredentialStore view feeds it to Models, which owns refresh, login and streaming.

after — ai/credential-store.ts (the whole bridge to pi)
// pi keys credentials by providerId; ai is single-active, so it maps to the one
// connection the activeAi pointer selects.
function aiCredentialStore(connections: ConnectionStore, activeAi: ActiveAiStore): CredentialStore {
  const conn = async () => { const a = await activeAi.get(); return a && connections.get(a.connectionId) }
  return {
    read:   async () => (await conn())?.creds as OAuthCredential | undefined,
    list:   async () => (await conn()) ? [{ providerId: 'openai-codex', type: 'oauth' }] : [],
    modify: async (_pid, fn) => { const c = await conn(); const next = await fn(c?.creds as Credential)
              if (next && c) await connections.put({ ...c, creds: next as Creds }); return next },
    delete: async () => { const c = await conn(); if (c) await connections.delete(c.id) },
  }
}
after — ai/host.ts
import { createModels } from '@earendil-works/pi-ai'
import { openaiCodexProvider } from '@earendil-works/pi-ai/providers/openai-codex'

function aiHost(connections: ConnectionStore, activeAi: ActiveAiStore) {
  const models = createModels({ credentials: aiCredentialStore(connections, activeAi) })
  models.setProvider(openaiCodexProvider())        // ships its own login + refresh

  return implementCapability(ai, {
    generateText: async (_c, { system, prompt }) => {
      const sel = await activeAi.get()
      if (!sel) throw new CapabilityError('CAPABILITY_UNAVAILABLE', 'ai')
      const model = models.getModel('openai-codex', sel.model) ?? models.getModels('openai-codex')[0]
      const res = await models.completeSimple(model,
        { systemPrompt: system, messages: [{ role: 'user', content: prompt, timestamp: Date.now() }] })
      return { text: textOf(res) }
    },
  })
}
// agent backend seam is the same Models + model → Ai = { models, model }
Option C — no codex-oauth.ts, no apiKeyBackend, no manual refresh, no /compat — is this. Login is models.login('openai-codex','oauth', interaction); aiCredentialStore.modify persists the connection.

D. The account-centric view survives as a façade

The Settings “Internet Accounts” UX stays. The accounts admin contract (listProviders/listAccounts/connect/setEnabled/disconnect → AccountInfo/ProviderInfo) is unchanged; it becomes a thin assembler over connections + derivation + the active-AI pointer. (This is exactly the shim landed in step 1: account-view.ts.)

// listAccounts: assemble the account-centric matrix — enablement is derived
listAccounts: async () => {
  const [conns, sel] = await Promise.all([connections.list(), activeAi.get()])
  return conns.map(c => ({
    accountId: c.id, providerId: c.kind,
    enabled: [backs(c,'email') && 'email', backs(c,'calendar') && 'calendar',
              sel?.connectionId === c.id && 'ai'].filter(Boolean),
    config: sel?.connectionId === c.id ? { ai: { model: sel.model, models: aiModels() } } : {} }))
},

// setEnabled writes the connection's scopes (email/calendar) or the pointer (ai)
setEnabled: async (_ctx, { accountId, capability, enabled, config }) => {
  if (capability === 'ai')
    await activeAi.set(enabled ? { connectionId: accountId, model: (config as any)?.model } : null)  // single
  else
    await grantScope(accountId, capability, enabled)   // widen (incremental consent) / drop the scope
}

Because AccountInfo/ProviderInfo and the RPC methods are untouched, packages/app-settings compiles and runs as-is.

Costs & migration order

  • Soft-disable becomes scope-drop. Today you can uncheck a service and keep the token’s scope; deriving from scopes means “disable email” drops the Gmail scope from the connection (re-enabling re-consents). This matches Composio/Arcade and is simpler. If a soft mute is ever needed, it’s a field on the connection (muted?: CapabilityId[]), not a store.
  • Form providers are all-or-nothing. An iCloud connection backs calendar by kind (no scope to toggle) — connecting it enables calendar. Reasonable: to stop iCloud calendar, disconnect it.
  • Storage migration. /system/accounts/*.json → /system/connections/*.json + one /system/active-ai.json. Idempotent; reconstructs scopes from each old account’s enabled set so backs() reproduces exactly what was on. (Implemented: migrate.ts.)
  • Incremental consent has a home. Google email→calendar scope-widening lives in a shared google-oauth helper the façade’s setEnabled composes with — not a generic Provider.scopes field.
  • Provider-id alignment. Store the ChatGPT connection under kind: 'chatgpt' and map to pi’s 'openai-codex' in aiCredentialStore (one line), or adopt 'openai-codex' as the kind.
