# App-Code Built-In Devkit Sysroot

## Context

The `dist/bundle.js` removal is done in code: built-ins are now file-backed through
`builtinSourceFromFs`, app manifests support `include`, and quay/desktop seed built-ins from
real app files instead of generated byte modules. That clears the path for app-code to ship
larger devkit files without embedding them as base64 JavaScript.

The remaining question is what app-code should be as a development environment.

We decided **not** to make app-code a complete npm-compatible dev environment. Supporting
arbitrary npm packages means reproducing package install, dependency resolution, lifecycle
scripts, caches, private registries, type acquisition, lockfiles, cleanup, and sandboxing. That
is too much product and maintenance surface for this project.

Instead, app-code is a small built-in authoring tool for Justfiles apps:

- supported imports are the platform SDK and a small built-in surface;
- the SDK (`@justfiles/app`, its capability subpaths, `valibot`) and React are provided by the
  host as **shared runtime modules** — a draft links against them, it does not bundle them;
- TypeScript declarations for that built-in surface ship with app-code (the "headers");
- external npm packages are intentionally unsupported in app-code;
- authors who need arbitrary packages should use `packages/create-app/` and a normal package
  workflow.

This document describes **how all Justfiles apps link the SDK**, not just app-code drafts — the
model below applies uniformly to built-ins, user-installed apps, and devkit previews (see
"Channels").

## Sources and Lessons

- [Sandpack](https://github.com/codesandbox/sandpack) is open source and separates the editor
  UI from a bundler/runtime client. Its [hosting the bundler guide](https://sandpack.codesandbox.io/docs/guides/hosting-the-bundler)
  explains why their bundler is isolated in an iframe/subdomain and cached separately. Lesson:
  do not mix editor UI and build runtime too tightly; keep the devkit as a host/toolchain seam.
- Sandpack's [local dependencies guide](https://sandpack.codesandbox.io/docs/guides/local-dependencies)
  prebundles a local package and presents it through a package-shaped file set. Lesson: a fixed
  SDK/sysroot is reasonable, but it is not the same thing as supporting arbitrary npm packages.
- [Vite TypeScript docs](https://vite.dev/guide/features.html#typescript) explicitly separate
  fast transpilation from `tsc --noEmit` typechecking. Lesson: keep `compile` and `typecheck`
  as separate devkit operations; a bundler is not a typechecker.
- [Bun single-file executable docs](https://bun.com/docs/bundler/executables) show quay can ship
  a Bun runtime and run a real toolchain.
- [WebContainers](https://webcontainers.io/guides/introduction) show what full browser-side Node
  requires; too opaque and too large for us to reproduce or depend on.

**Prior art for "externalize the platform SDK; the host provides it at runtime" (this is the
established pattern, we are on the grain of it):**

- [VS Code extensions](https://code.visualstudio.com/api/working-with-extensions/bundling-extension)
  — our closest twin (Node-side, like our reducer). Extensions mark `externals: { vscode:
  'commonjs vscode' }`; the `vscode` module "**does not exist on disk but is created by VS Code
  on-the-fly when required**." → externalize the SDK + host injects it **from memory**, never a
  bundled or on-disk copy.
- [MDN: import maps](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/script/type/importmap)
  — definitive: an import map applies to documents and "**does not apply to … modules loaded into
  workers or worklets**"; workers must use full/absolute URLs or implement their own resolution.
  This is *why* the gui (a document) uses an importmap and the reducer (a worker) cannot — it
  needs URL/injection. We follow the platform here, not fight it.
- [Webpack Module Federation `shared`](https://module-federation.io/configure/shared) —
  externalize shared deps, resolve them at runtime from an in-memory "Share Scope," with
  `singleton` + `requiredVersion` + version negotiation. Confirms the model, and shows the
  *mature* end-state includes version-negotiation machinery (which we deliberately defer; see
  "Version skew").
- [Figma plugins](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/) — plugin code
  runs in a minimal sandbox; the `figma` API is injected by the host at runtime (not bundled).
- Apple `dyld` / dylibs — the version-ownership / ABI-stability framing this design adopts.

Two takeaways shaped the design: (1) **memory injection is the norm; staging the SDK to disk for
the sandbox to read is the outlier** — so we inject in-memory and keep no disk cache; (2) version
negotiation is the known mature extension, reasonable to defer while host and apps are
co-versioned.

## SDK linkage model (the core decision)

The SDK is **externalized, not bundled** — the platform-framework model (UIKit / dylib / VS Code's
`vscode`): the host provides the framework, the app is mostly its own code, and SDK calls reach for
the shared library. This is safe here because — unlike React — the SDK has no hard single-instance
requirement (`defineApp` / `defineGUI` / the capability factories are pure functions returning plain
`{ id, scopes }` config; validation runs within each side consistently). React is already
externalized this way; we extend the same treatment to `@justfiles/app`, its capability subpaths,
and `valibot`.

**Why externalize rather than bundle — version ownership.** An installed app must link the
**system's current** SDK at launch, not a copy frozen at install time. A bundled SDK strands the
app: a later kernel/protocol change breaks an app whose code is still 100% correct and whose API
never changed, recoverable only by author recompile (the iOS "OS update broke my app, resubmit with
zero changes" anti-pattern). Externalizing makes that impossible — the app carries only a *reference*
to the SDK; the system owns the implementation behind it and keeps it working.

This splits the old "sysroot" into two halves with two different owners:

- **headers → app-code.** TypeScript declarations are still needed to typecheck AND to compile
  against (a UIKit app compiles against headers even though the framework is external). App-code
  ships these as a **types-only** sysroot.
- **the runtime → the host.** The host owns **one** SDK build (`buildRuntime()`'s output) and
  provides it to apps at runtime. App-code's sysroot carries **no** runtime.

### The two link seams

A draft runs in two contexts; how the reference resolves to the current system SDK differs, because
(per MDN above) **workers have no import map**:

| Context | Where it runs | Link seam → current system SDK |
|---|---|---|
| `gui.js` | host webview / main document | **importmap** — bare specifier (already resolves React; add SDK specifiers) |
| `app.js` (reducer) | a module `Worker` (`data:`/`blob:` URL) | **sentinel rewritten at spawn** → an in-memory module the worker can load (below) |

The reducer worker can't resolve bare specifiers and has no importmap, so the compiler emits a
host-agnostic **sentinel** specifier (`import { … } from "justfiles-sdk:@justfiles/app"`) and **each
host rewrites it at spawn** to a module the worker can load:

- **browser (frieren):** rewrite to the **served** `${location.origin}/vendor/@justfiles/app.js`.
  The blob worker fetches it same-origin (proven in the prior spike, Step 0). A root-absolute
  `/vendor/...` does **not** resolve inside a blob worker — it resolves against the `blob:` base,
  which has no host — so the origin must be included.
- **node/bun (quay/desktop):** rewrite to a **`data:`/`blob:` URL of the host's in-memory SDK**,
  produced by the same per-runtime `moduleUrl()` the host already uses for the app bundle (data: on
  node, blob: on bun). No `file://`, no disk.

### No on-disk SDK cache — deliberate

There is **no** `file://` SDK cache, no boot-time staging, no per-app SDK directory. **Do not add
one.** The reducer SDK is injected in-memory at spawn (browser: the served vendor URL the worker
fetches; node/bun: a `data:`/`blob:` URL of the host's in-memory SDK). This is diskless, makes the
app bundle portable, gives the reducer worker no filesystem path, and matches the prior art (VS Code
creates `vscode` from memory; Figma injects from memory; Module Federation uses an in-memory Share
Scope). We considered baking a `file://` path + a host cache dir and **rejected it**: it is
host-specific (breaks off-host-built bundles — see Channels), adds staging/purge/versioned-path
machinery, and hands the worker a real fs path for no gain.

### This is not a Volume path

The Volume (`@justfiles/fs`) holds the *app*; `app.js` still reaches the worker as an in-memory
`data:`/`blob:` URL built from `code` read via `fs.readFile` (`kernel.ts:202`). The SDK is the
*host's own* artifact (its `buildRuntime()` output, already in memory) — the app merely imports it by
a stable reference rewritten at spawn. There is no Volume→OS-path conversion: the app stays
in-memory, the SDK is the system's.

## Channels (this model is uniform across all apps)

All Justfiles apps link the SDK the same way. There is no special case per channel — and crucially,
**all three channels converge on a single reducer spawn seam** (`GetSandbox`), which is where the
sentinel is rewritten:

1. **Built-in apps** — built at CI by `kernelHost` (`packages/app/vite.ts`), seeded via
   `builtinSourceFromFs`, run through `kernel.ts:202` → `GetSandbox`.
2. **User-installed apps** — installed from the IDE (app-code), a dragged-in zip
   (`bundleFromZip`), or a future app store; written to the Volume; run through the same
   `kernel.ts:202` → `GetSandbox`.
3. **Devkit preview** — app-code's live preview. The preview runner installs the built draft into a
   kernel and runs it through the normal path (quay mounts into "the same kernel the booters serve
   from"; frieren `createClientKernel` + `kernel.install`) → the same `GetSandbox`.

Because off-host-built bundles (built-ins at CI, dragged zips, store downloads) **cannot know** a
host's paths at build time, the SDK reference must be host-agnostic and resolved at the host —
exactly what the sentinel + spawn-rewrite gives. This is why externalization must be uniform and why
both compile paths (`kernelHost` AND the devkit toolchain) externalize identically. **There is no
"builtins stay bundled" carve-out** — built-ins externalize like everything else; they remain
co-released with the host, so they also benefit from the version-ownership guarantee.

## Final Design

App-code ships a **types-only** sysroot; the host owns the SDK runtime.

```text
packages/app-code/dist/
  manifest.json             # includes ["devkit/**"]
  app.js
  gui.js
  devkit/
    index.json              # schema, hash (the SDK allowlist is the host's, not shipped here)
    types/
      @justfiles/app/...     # the "headers" — keyed for tsc resolution
      @justfiles/fs/...
      @types/react/...
      @types/react-dom/...
      valibot/...
```

`devkit/index.json`:

```json
{
	"schema": "justfiles.devkit.v1",
	"hash": "sha256-…"
}
```

There is deliberately **no** `external` array in `index.json`. The SDK + React allowlist
is the host's — the toolchain runs *in* the host (quay's `#engine`, frieren's
esbuild-wasm) and reads a single compiled-in constant (Step 4). Shipping a copy here
too would just reintroduce the drift it's meant to prevent (an app-code built with a
newer list run against an older host). The host owns the runtime; the host owns the
allowlist that resolves against it.

Naming/structure decisions (carried from the structure review):

- the index is `index.json` — generic, and namespaced by the `devkit/` dir it sits in. Not a second
  nested `manifest.json` (grep-unambiguous against the bundle's top-level `manifest.json`, and dodges
  tooling that special-cases `manifest.json`);
- `schema` (not `version`) matches the existing `Catalog.schema` convention
  (`builtins.fs.ts:8` = `justfiles.appstore.v1`); `hash` is the content version and the cache key;
- `hash` covers the sorted `(path, contentHash)` of all `devkit/types/**`, so any header change
  flips it. With `external` gone, `index.json` is just `schema` + `hash`, so hashing the whole
  file is equivalent if simpler to implement.
- there is **no** `runtime/` directory and **no** `runtime` map — the runtime is the host's.

Types: the loader reads the whole `devkit/types/` subtree into a `TypesBundle` keyed
`node_modules/<pkg>/…` (the tsc overlay needs that key). To avoid shipping a literal `node_modules`
directory inside the bundle (npm/pnpm publish strip it, some bundlers/IDEs special-case it), store
the tree as `devkit/types/<pkg>/…` and have the loader prepend `node_modules/` when building the
bundle key. The Step 6 "typecheck with no node_modules" test guards this.

The SDK + React allowlist is the compile allowlist for **both** entries and **both** compile paths
(`kernelHost` and the devkit toolchain): the resolver marks these specifiers external, then per
entry-kind either leaves the bare specifier (gui) or rewrites to the sentinel (reducer). It is a
single shared constant (see Step 4) imported directly by both resolvers, so the app-code surface and
both resolvers cannot drift. It is the *only* copy — it is not also shipped in `index.json`.

The compiler is hermetic and **entry-kind-aware** (it must be told whether it is compiling the gui
or the reducer entry, since `app.js` and `gui.js` are separate `compile` calls):

- relative imports resolve within the draft project;
- for `gui.js`: SDK + React imports are **external** as a bare specifier (the host importmap
  resolves them in the document at runtime);
- for `app.js` (reducer): SDK imports are **external** rewritten to the **sentinel**
  `justfiles-sdk:<spec>` (the host resolves it at spawn — Step 3); the reducer imports no React;
- any other bare import is unsupported and produces a clear diagnostic (Step 8).

### 2. Externalize the SDK in BOTH compile paths (entry-kind-aware) (DONE ✅)

**Done (2026-06-22).** Both compile paths externalize the SDK; the reducer carries the
`justfiles-sdk:` sentinel.

- **shared rules** (`packages/app/sdk-externals.ts`): `SDK_SENTINEL = 'justfiles-sdk:'`,
  `isSdkSpec(spec)` (the bare-externalize predicate), and `sentinelizeReducer(js)` (rewrites a
  compiled reducer's bare SDK imports → sentinel). One home both compile paths import. (Step 3
  reworked `sentinelizeReducer` from a regex to an `es-module-lexer` walk — a regex corrupted
  import-like substrings inside string literals, e.g. Code's embedded starter template; see Step 3.)
- **bare-externalize-then-rewrite, not in-resolve.** The original plan assumed each resolver
  rewrites to the sentinel in `onResolve`. That works for esbuild but **Bun keeps the original
  specifier for `external` imports** — it ignores both `path` and `namespace` in an `onResolve`
  result (verified with a throwaway on bun 1.3.7). So both bundlers externalize the SDK as a
  **bare** specifier and the **reducer** output is rewritten in one shared post-build pass
  (`sentinelizeReducer`), which works uniformly. React stays external via each bundler's
  top-level `external: reactExternals` (it also catches the auto-injected JSX-runtime import).
- **devkit toolchain** (`toolchain.vfs.ts` + esbuild/bun adapters): the adapters mark SDK specs
  external bare (`isSdkSpec`); `compileVfs` sentinelizes the reducer entry (`name !== 'gui'`).
  The gui keeps bare specifiers for the importmap.
- **kernelHost** (`vite.ts`): the gui lib build's `rollupOptions.external` is now `externals`
  (React + SDK bare, importmap-resolved); the reducer `compile()` uses esbuild `external:
  externals` + `sentinelizeReducer`. (Serve-mode `resolve.dedupe` → `reactExternals`.)
- **`runtime` map kept threaded for now.** SDK externalization takes precedence over the
  (now-inert) `runtime` injection in the adapters; the host-side `runtime`/`runtime.json` /
  `virtual:devkit-runtime` removal stays Steps 7/10.

Verified: the esbuild and Bun toolchains emit gui-bare / app-sentinel; the externalized reducer
dispatches once its sentinels are resolved to `data:` URLs of the host SDK (valibot named
exports intact, multi-module no-singleton) — `packages/app/devkit.test.ts`; a `kernelHost`-built
`app-counter` emits `justfiles-sdk:@justfiles/app` + `justfiles-sdk:valibot` in `app.js` and bare
`@justfiles/app/browser` in `gui.js` (`defineGUI` not inlined → shrinks); the react-free guard
still passes. `pnpm format`/`typecheck`/`lint:fix`/`test` (696) + the bun toolchain tests all green.

  `data:`/`blob:`); neither inlines the SDK;
- a host SDK rebuild is picked up by an already-installed app **without recompiling it** (the dylib
  property) — rebuild the host SDK, restart the daemon, the unchanged installed app still runs;
- `kernelHost`-built built-ins externalize too (no bundled SDK in `app.js`/`gui.js`);
- the react-free reducer guard fails the build if a `react` import sneaks into SDK core/capabilities;
- a reducer that imports SDK *core + a capability + valibot* together resolves all three sentinels to
  separate self-contained vendor modules and round-trips a valibot-validated payload — a **unit test**
  confirming the no-singleton assumption holds across the duplicated SDK copies. (No *runtime* guard
  is needed: the host injects the same SDK into every app at spawn, so there is nothing to drift or
  guard at runtime — the test pins the assumption, not the wiring.)
- typecheck works using only installed app-code headers (no node_modules);
- React JSX emits production-compatible imports;
- unsupported imports fail clearly; real type errors are still caught.

### 12. (Optional, later) node/bun memory loader-hook

An optional refinement for node/bun only. Instead of rewriting the sentinel to a `data:`/`blob:` URL,
register a module customization hook (node `module.register()` / a bun plugin) in the worker that
resolves `justfiles-sdk:<spec>` and serves the SDK source straight from memory. Reason to consider it
later: it avoids embedding the SDK bytes into each spawn's `data:` URL (smaller per-spawn strings) and
is the same mechanism VS Code uses for `vscode`. Reason it's not the baseline: more per-runtime
machinery (a registered hook + data channel into the worker), and the `data:`/`blob:` rewrite already
works uniformly and is diskless. Revisit only if per-spawn `data:` size becomes a measured problem.

## Version skew (accepted tradeoff)

Externalizing **both** halves adopts the dylib deal in full: an installed app links the host's
**current** SDK at launch (gui via importmap, reducer via the spawn-rewritten module), and the
system — not the author — owns keeping it working (full rationale under "Why externalize rather than
bundle" above).

The obligation this creates: the system must keep the SDK's **runtime exports backward-compatible**,
because old installed bundles call the current SDK. That's the right obligation (what any OS
framework signs up for) and strictly better than bundling, where post-ship compat is impossible.

We do NOT yet have the finer machinery that mature systems use for cross-version compat —
[Module Federation](https://module-federation.io/configure/shared)'s `singleton`/`requiredVersion`
negotiation, or Apple's `@available` / weak-linking / deprecation cycles. For now host and apps are
effectively co-versioned (apps authored in-IDE, run in the same host; built-ins co-released), so skew
is bounded, and "don't break SDK exports" is a discipline we take on. If apps ever need to span an
SDK-breaking change (the app-store future), that negotiation machinery becomes a real, separate cost.
Documented so the decision is explicit, not implicit.

## Non-Goals

- arbitrary npm package support in app-code;
- package manager UI; lockfiles; install scripts; private registries;
- WebContainer-style browser Node runtime;
- an on-disk SDK cache / staging for the reducer (deliberately diskless — see "No on-disk SDK
  cache");
- SDK version-negotiation / availability machinery (we accept co-versioned skew for now).

Those belong to normal package projects created with `packages/create-app/`.

## Open Questions

**Resolved.** The only open gate was **Step 0** (the in-memory injection spike): it is now **proven**
on node 26.2.0 (`data:`) and bun 1.3.7 (`blob:`) — a `data:`/`blob:` app module imports a
`data:`/`blob:` SDK module with named exports intact, including the multi-module (core + capability +
valibot) no-singleton case (see Step 0's result table). No per-runtime fallback is needed: the
diskless in-memory model holds. Everything else is implementation.

## Review notes (verified against the codebase)

- **Headers footprint is bounded.** ~30 `.d.ts` for the React family (`@types/react` 13 /
  `@types/react-dom` 14) plus valibot / type-fest / `@justfiles/*` — well under ~1 MB, sha256'd once.
- **No type-version skew from owning the bake in app-code.** `@types/react` resolves from the hoisted
  pnpm store (`@types+react@19.2.7`); both `@justfiles/app` and `@justfiles/app-code` depend on that
  one version, so baking from app-code yields identical bytes.
- **Externalization buys version ownership, not byte-dedup.** Each reducer runs in its own `Worker`
  realm (`nodeSandbox.ts`), so externalizing wins nothing on *sharing*; the point is that the
  installed app links the *system's current* SDK at launch, not a copy frozen at install (`code` off
  the Volume, `kernel.ts:202`; only the SDK *reference* is external, resolved at spawn).

reducer surface, the safe-to-externalize property, and diskless-matches-prior-art — are asserted in
