write-then-publish

Closing the create-then-fill visibility gap in writeFile's exclusive claim — what it fixes, why the fix we already shipped wasn't enough, and why the real fix eliminates the whole problem class instead of one instance of it.

The one idea. A claim (writeFile(path, data, { exclusive: true })) is currently two storage calls: claim the name, then fill the content. Between them, the name is visible with no content behind it. Every mature system that solves this (Maildir, Git objects, LSM engines) agrees on the fix: write the content first, somewhere uncontested, and only publish the name once the content is already durable. We have the primitive for that already (ContentStore.putByHash) — writeFile just doesn't use it yet.

1 · The bug, in one picture

Two callers race to create /.state/clientid — say, deviceId() on one Volume wrapper and synced()'s own boot sequence on a second wrapper over the same underlying storage. The atomic claim (atomicCreate, backed by O_CREAT|O_EXCL–style semantics) correctly picks exactly one winner — that part was always right. 2 · Why the first fix (PR #318) wasn't enough

The review on #318 first flagged that device.ts's own write wasn't exclusive — fixed by moving the claim into persistedState.ts's get(), so synced() and deviceId() share one atomic-claim implementation instead of two that could drift.

That closed "two different UUIDs, both written, one silently clobbers the other". It did not close "the winner's UUID exists as a name microseconds before it exists as bytes" — a different bug, one level down, in writeFile itself. The fix that shipped works around it with a bounded poll (awaitWinner): the loser retries the read a few event-loop turns until the winner's putBlob lands. That's correct, but it's a symptom patch — every future exclusive-write caller (there are already three: device ids, sync state, and app-notes' claimPath) would need its own copy of the same poll loop, for the same reason, forever.

3 · The fix, in one picture

Reorder the two calls. Hash the content and store it under its hash before claiming the name, using the hash-addressed ContentStore we already have (built for the sync/pull path, unused by local writes). By the time the name becomes visible to anyone, the bytes behind it are already durable — because publishing the name is the last step, not the first.

4 · This is well-trodden territory

The question worth asking before rewriting a concurrency primitive is "has literally everyone else hit this and how did they get out". They have, and they agree:

SystemWhat it doesSame shape as our fix
Maildir (Bernstein) Write the full message into tmp/, only rename() into new/ once complete. Content fully written before the name that makes it "delivered mail" exists.
Git loose objects Write the blob to a temp file under .git/objects/, link()/rename() to its sha1 path once done. The name is the content hash — it can't be published until the bytes it names exist.
LevelDB / RocksDB Write a new SSTable under a private filename, fsync, then flip the MANIFEST pointer. Payload durable first; the pointer swap is the atomic "publish" step, last.
SQLite (own docs) Explicitly distrusts "file size grows, then content fills in" as a source of garbage reads. Names the exact bug shape we hit, on a different substrate.
etcd / ZooKeeper / Chubby Compare-and-swap on a revision, not a lease/lock, for "create if absent, one winner". The claim half of our fix (already shipped, already correct).

The reassuring part: we're not missing something dumb about filesystems. We're missing one specific, well-documented ordering choice — and we already built the primitive (ContentStore.putByHash) that the fix needs, for an unrelated reason (the sync/pull path). It's just not wired into the local write path yet.

5 · What changes, concretely

Before name, then content
// volume.ts, writeFile() creation branch
ino = await createNode(dirIno, name, {
  type: FileType.Regular,
  size: 0n,
  mode, mtimeNs, ctimeNs
  // no contentHash yet
})
await storage.putBlob(ino, data)
// ^ window: `name` exists here, content doesn't
After content, then name
// volume.ts, writeFile() creation branch
const hash = await sha256Hex(data)
await storage.caps?.content?.putByHash(hash, data)
ino = await createNode(dirIno, name, {
  type: FileType.Regular,
  size: BigInt(data.length),
  contentHash: hash,   // already known
  mode, mtimeNs, ctimeNs
})
// no trailing putBlob — content was already durable

Net effect on persistedState.ts: awaitWinner()'s poll loop (for (...) { try read() catch retry-after-tick }) shrinks to a single read() — there's nothing transient left to retry.

6 · Why this is its own issue

  • Blast radius. writeFile's creation path is used by every caller, not just exclusive claims — the reorder has to be proven neutral for the common case too.
  • Backend surface. Only backends with the content cap (mem, IDB, node) can take the fast path; the fallback for backends without it must stay byte-identical to today.
  • Test surface. exclusive.test.ts, sync-units.test.ts, synced.test.ts, and sync-conformance.test.ts all touch this code path and need to stay green, unmodified, alongside new RED cases for the gap itself.
