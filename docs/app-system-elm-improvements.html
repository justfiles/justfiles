Elm lessons for @justfiles/app

A short improvement report for the kernel app system, ordered so each step creates the semantic foundation for the next.

Elm baseline

  • Cmd msg is a one-shot outside-world request. The runtime performs it and later sends a msg.
  • Sub msg is an ongoing outside-world listener. The runtime starts/stops it based on subscriptions model.
  • Neither mutates state. Everything becomes a message, and only update creates the next model.
  • The model stores the UI's current projection of the world, not the whole world. For an IDE: paths, versions, visible chunks, dirty/stale flags, preview URLs, etc.

Target loop

Execution order

  1. 1Serialize dispatch per app

    All public actions, command results, and subscription events must enter one queue. Without this, two events can load the same state and last-write-wins.

    const tails = new Map<AppId, Promise<void>>()

function enqueue<T>(appId: AppId, work: () => Promise<T>): Promise<T> {
	const prev = tails.get(appId) ?? Promise.resolve()
	const run = prev.catch(() => undefined).then(work)
	tails.set(appId, run.then(() => undefined, () => undefined))
	return run
}

async function dispatch(appId: AppId, action: Action): Promise<unknown> {
	return enqueue(appId, () => dispatchNow(appId, action))
}

    This is the most important semantic fix. Do it before subscriptions.

  2. 2Materialize initial model before GUI mount

    Today GUIs receive null and duplicate initialState. Elm programs always start with a model. The kernel should persist or at least provide the app's initial model before the first GUI render.

    export const app = defineApp({
	init: { files: [], currentViewing: null, loading: true, error: null },
	actions: (b) => ({ ... })
})

// target GUI shape
mount(el, state, ctx) {
	// state is FinderState, not FinderState | null
}

    After this, remove app-local stateOrInitial() helpers from example GUIs.

  3. 3Formalize private runtime messages

    Elm has one Msg type, but not every message is public. Our public actions are also agent tools, so runtime messages should stay hidden from kernel.actions().

    export const app = defineApp({
	init,
	actions: (b) => ({
		refresh: b.handler({ ... }) // public: GUI/agent can call
	}),
	on: {
		volume: {
			changed: (event, ctx) => ({ ...ctx.state, stale: true }) // private
		},
		runtime: {
			tick: (_event, ctx) => ({ ...ctx.state, now: Date.now() }) // private
		}
	}
})

    Current __event/* synthetic actions are the right implementation direction. Make the interface explicit; keep them hidden from agents.

  4. 4Add model-derived subscriptions

    Current on handlers are static. Elm's key move is subscriptions(model): the model decides what the runtime should listen to right now.

    export const app = defineApp({
	init,
	capabilities: {
		volume: volume({ scopes: ['system'] }),
		runtime: runtime({ scopes: [] })
	},
	actions: (b) => ({ ... }),
	on: {
		volume: {
			changed: (e, ctx) =>
				e.path === ctx.state.currentViewing
					? { ...ctx.state, stale: true }
					: ctx.state
		},
		runtime: {
			tick: (_e, ctx) => ({ ...ctx.state, clock: ctx.state.clock + 1 })
		}
	},
	subscriptions: (state, s) =>
		s.batch([
			s.runtime.every({ ms: 1000 }, 'runtime.tick'),
			state.currentViewing
				? s.volume.watch({ path: state.currentViewing }, 'volume.changed')
				: s.none()
		])
})

    The kernel/runtime should diff the returned subscription description after every state change and start/stop adapters.

  5. 5Create a subscription adapter seam

    Capabilities are our Elm effect managers. They should own the messy runtime listener code; app authors should only declare subscription data.

    type SubscriptionEvent = { channel: string; payload: unknown }
type Stop = () => void

interface SubscriptionAdapter {
	key(input: unknown): string
	start(input: unknown, emit: (event: SubscriptionEvent) => void): Promise<Stop> | Stop
}

    Initial adapters:

    • runtime.every → timer ticks.
    • volume.watch → file/tree changes.
    • Later: integrations/account changes, online/offline, visibility, calendar/email pushes.

    Start with browser/open-window subscriptions only. Durable Object/background subscriptions are a separate product decision.

  6. 6Add managed commands/effects only after the loop is solid

    Our current async handlers can keep working. Elm-style commands become useful once the queue, init, private messages, and subscriptions exist.

    type AppResult<State> =
	| State
	| [State, AppEffect]

handler(_, ctx): AppResult<FinderState> {
	return [
		{ ...ctx.state, loading: true },
		fx.capability('volume', 'scan', { path: '/', recursive: true }, 'volume.scanned')
	]
}

    @justfiles/state effects are post-reducer side effects. They are not Elm Cmd at the app interface. Reuse the idea, not the exact interface.

  7. 7Fix query semantics

    Current comments say queries are pure reads, but examples use them for writes (Paint.saveDraft, Code.install). Pick one:

    • Strict: query must be read-only; writes are handlers/effects.
    • Pragmatic: rename to call: may touch capabilities, but does not persist app model.

    Do this before agents/tooling depend more heavily on ActionMeta.kind.

IDE / Finder model rule

Do not store the whole filesystem, giant files, images, editor undo stacks, or viewport caches in persisted app state. Store the semantic projection needed by the app and agent.

type IdeState = {
	root: string
	expandedDirs: string[]
	tree: Record<string, { status: 'loading' | 'loaded'; children?: string[] }>
	current: null | {
		path: string
		version: string
		kind: 'text' | 'image' | 'binary'
		stale: boolean
		textPreview?: { offset: number; text: string; truncated: boolean }
		imageUrl?: string // blob/asset URL; pixels stay outside model
	}
	diagnostics: Array<{ path: string; line: number; message: string }>
}

For a coding editor, let a deep GUI/editor module own transient buffers, cursors, token caches, scroll, and undo. The app model owns paths, versions, dirty/stale state, diagnostics, build status, and any small rendered previews.

What not to do

  • Do not let subscriptions mutate state directly. They emit private messages/actions.
  • Do not expose runtime messages as public agent actions.
  • Do not add background subscription machinery before browser/open-window subscriptions prove the interface.
  • Do not force huge resources into kernel state just to imitate Elm. Keep the pure model idea, but respect our GUI/editor seam.

Suggested migration slice

  1. Add per-app queue tests in packages/app/kernel.test.ts.
  2. Persist/provide initial model; migrate Counter/Finder/Settings GUI away from nullable state.
  3. Expose private runtime messages cleanly over the existing __event/* implementation.
  4. Add browser-only runtime.every and volume.watch subscriptions.
  5. Move Finder/app-code first-load/watch logic out of GUI useEffect where practical.
  6. Then evaluate managed commands/effects and the query rename.
