Capability subsystem · implementation plan

The Capability system — a complete, pluggable concept

Turn capabilities from per-backend copy-paste into a Volume-grade subsystem: a tiny set of composable primitives in packages/app, thin host implementations outside, and one streaming wire protocol that carries subscribe across any backend — with finder/code file-watching as the first stream it lights up.

Carried over from app-kernel-capability-host.html (settled)

  • One request type CapabilityCall = { appId, capability, method, input, scopes, actor? }.
  • One seam Capabilities { invoke(call); subscribe(call, emit) } — injected as capabilities? on System.
  • subscribe, not stream — the return type is Unsubscribe; the whole feature already speaks “sub”.
  • Two seams, one substrate: machine.ts is the unified event port (opaque Effect/Message); Capabilities is the typed interpreter where 1:1 becomes a Promise and 1:N becomes (emit)=>Unsubscribe.
  • Scopes are trusted & kernel-attached — resolved from the app's bundle, never from the isolate. CapabilityCall.input stays unknown at the seam; types live at the ends.

This plan builds on top of those and does not re-argue them.

Where we are: a half-built concept

The reason capabilities feel ad-hoc next to Volume is concrete — the contract half already lives in the package, but the machinery half is reimplemented in every backend, and even the parts that are in the package are invoke-only and fragmented.

So the work is not “invent a capability system” — it's finish the one that's started: grow the invoke-only bridge into the invoke+subscribe seam, give it a router, one error vocabulary, an implementation-definer that pairs with the existing contract-definer, and a wire protocol that carries both legs.

The goal: Capability should compose like Volume

@justfiles/fs ships Volume (the interface) plus combinators (chroot(vol, prefix)) and backends (memStorage); a consumer composes them. Capabilities get the same anatomy:

A backend is then impls + one wiring line; nothing re-derives routing, errors, ids, or transport.

The layering (the spine)

Everything above the seam is unchanged kernel work. Everything below it is the subsystem this plan completes.

The authoring surface — “what” and “how”

This is the part to keep ruthlessly minimal. An implementer answers exactly two questions, and nothing else — no registration, no error plumbing, no transport, no ids.

What can you do? — the contract (exists today)

// packages/app/capabilities/volume
export const volume =
  defineCapability<'volume',
    VolumeCapability,   // one-shot methods
    VolumeStreams>(     // Stream<Event> methods
    'volume')

How do you do it? — the implementation (new)

// host side — a flat object of typed fns
export const volumeCapability = (fs: Volume) =>
  implementCapability(volume, {
    readFile:  ({ path }, ctx) => vol(fs,ctx).readFile(path),
    writeFile: ({ path, data }, ctx) => vol(fs,ctx).writeFile(path, data),
    exists:    ({ path }, ctx) => vol(fs,ctx).exists(path),
    scan:      ({ path, recursive }, ctx) => scan(vol(fs,ctx), path, recursive),
    // a stream: "here's the callback, call it when it happens"
    watch:     ({ path }, emit, ctx) => vol(fs,ctx).watch(path, emit),
  })

The whole rule, stated once

  • A unary method is (input, ctx) => output.
  • A stream method is (input, emit, ctx) => Unsubscribe — receive the callback, call it on each event, return the teardown. That is the entire stream contract.
  • ctx = { appId, scopes, actor? } — the trusted metadata the kernel already attached (scope→resource resolution lives here, e.g. resolveVolume). Capabilities that don't need it ignore it.
  • Failures: throw new CapabilityError(code, …). The registry/seam turn it into the right result/wire shape. The impl never formats errors.

The author writes one object of typed functions. Which arm of the seam each lands behind (invoke vs subscribe) is decided by the kernel — it only ever calls subscribe for methods the app declared as Streams — so the implementation never thinks about routing.

The registry — one router, with a fallback

Collapse the six hand-written if-chains into one combinator. The optional fallback is exactly today's browser behaviour (volume/devkit local, everything else proxied):

function capabilityRegistry(
  map: Record<string, Capability>,
  opts?: { fallback?: Capabilities },
): Capabilities

Before — frieren, repeated ×3 backends

function invokeCapability(req) {
  if (req.capability === 'ai') { … }
  if (req.capability === 'volume') return invokeVolume(…)
  if (req.capability === 'integrations') { … }
  throw capabilityError('UNAVAILABLE', …)
}
// …and a near-identical streamCapability

After — one line per backend

// browser kernel
capabilityRegistry(
  { volume: volumeCapability(fs), devkit: devkitCapability(fs) },
  { fallback: proxyCapabilities(channel) },
)

// server kernel
capabilityRegistry({
  volume: volumeCapability(fs),
  ai: aiCapability(text),
  integrations: integrationsCapability(reg),
})

One error vocabulary

Move the error concept into packages/app and unify the two fragmented code sets (frieren's UNAVAILABLE/INVALID_INPUT/OFFLINE and the broker's DENIED/FAILED) into one CapabilityError + wire codec. Every layer — impl, registry, proxy, broker — raises and relays the same shape, and integrations.capability.ts stops re-inlining codes by hand.

class CapabilityError extends Error { code; capability?; method? }
const CAPABILITY = { UNAVAILABLE, INVALID_INPUT, DENIED, FAILED, OFFLINE } as const
function toWire(e): WireError ; function fromWire(w, fallback?): CapabilityError

The frame protocol — subscribe across the wire (new scope)

Generalize the _caps socket from invoke-only to both legs, over an abstract Channel so CF Workers, a Node server, and Electron-main all fit the same proxy. The proxy is transparent: a remote capability is a Capabilities just like a local one.

// the only thing a transport must provide
interface Channel {
  send(frame: string): void
  onMessage(cb: (frame: string) => void): void
  onClose(cb: () => void): void
}

function proxyCapabilities(open: () => Promise<Channel>): Capabilities      // caller side
function serveCapabilities(channel: Channel, local: Capabilities): void        // provider side
LegDirectionFrame
invoke (1:1)C→S{ t:'call', id, appId, capability, method, input }
S→C{ t:'ok', id, value }  |  { t:'err', id, …wire }
subscribe (1:N)C→S{ t:'sub', id, appId, capability, method, input }
S→C{ t:'event', id, event }  (repeated)  |  { t:'err', id, …wire }
C→S{ t:'unsub', id }  (teardown → the returned Unsubscribe)

proxyCapabilities is the same pending-map correlation we already have for invoke, plus an id → emit registry for subscribe (route event frames to the live emit; unsub on teardown). serveCapabilities is today's handleMessage, plus: on sub, call local.subscribe(call, e => send event) and keep the returned Unsubscribe under id until unsub.

Trust note — scopes never cross the channel

Client-claimed scopes are untrusted (the current proxy already sends none). Scopes are attached by the kernel that owns the trusted bundle and executes the capability. So a proxied frame carries appId but not scopes; the serving side resolves scopes from its own copy of the app's declarations before invoking. Today's proxied capabilities (ai, integrations) are scope-free, so this is a no-op now and a clean rule for later.

The immediate win: finder & code watch the volume

volume already supports watch; what's needed is the subscribe path wired through as a first-class citizen. End to end:

  • Locally (browser kernel owns the synced volume) this needs no frames — it's the registry calling the local unit. This is what lights finder/code up.
  • Across the proxy the identical subscribe rides the new sub/event/unsub frames — the reference stream that proves both paths, and the principled replacement for today's ad-hoc dirty push (app.update → blanket flushActiveVolume()).

Acceptance: a file write to a watched path delivers exactly one fileChanged to the app, and leaving the watch's state stops the stream (reconciler diff → Unsubscribe).

What goes where

packages/app — the subsystem

  • CapabilityCall, Capabilities, Capability
  • defineCapability (exists), implementCapability (new)
  • capabilityRegistry
  • proxyCapabilities, serveCapabilities, Channel
  • CapabilityError + codes + wire codec
  • per-capability contracts (already here)

host (frieren / node / electron) — the bindings

  • volumeCapability(fs), aiCapability(text), integrationsCapability(reg), devkitCapability
  • the Channel adapter over its transport (WebSocket / IPC)
  • one capabilityRegistry({…}, { fallback? }) wiring line
  • scope→resource policy that's genuinely host-specific (e.g. resolveVolume)

A brand-new backend implements the bindings column and writes one registry line. That is the Volume-grade payoff.

Build order

  1. 1Seam + types. CapabilityCall, Capabilities, Capability; grow CapabilityBridge.invoke into the seam. Rename the kernel's internal resolver Capabilities → CapabilityResolver (frees the name). Wire System.capabilities?. No behavior change.
  2. 2Registry + one error vocabulary + implementCapability. Move capability-error into the package and unify codes; add the router and the impl-definer; port frieren's four impls onto them. Each backend collapses to one wiring line. Pure dedup.
  3. 3Local subscribe end-to-end. Carry subscribe through the registry; finder/code watch the volume locally. Acceptance test above. First user-visible win.
  4. 4Frame protocol, both legs. Channel, proxyCapabilities, serveCapabilities with call/ok/err + sub/event/unsub. Re-point frieren's _caps socket at them; the proxied volume watch exercises the sub leg and retires the dirty hack.

Phases 1–2 are mechanical and strictly remove code; 3 is the feature; 4 is the only one with real protocol design and should land on its own.

The entire public surface

The minimality test — everything an app author, a host implementer, or a new backend ever touches:

// types
CapabilityCall, Capabilities, Capability, Channel, CapabilityError, WireError

// app author (contract)            — already exists
defineCapability<Id, Methods, Streams>(id)

// host implementer (one unit)
implementCapability(contract, { [method]: (input, ctx) => out
                              , [stream]: (input, emit, ctx) => Unsubscribe })

// backend wiring (combinators)
capabilityRegistry(map, { fallback? })
proxyCapabilities(open)            serveCapabilities(channel, local)

Six types and five functions, two of which already exist. An implementer's mental model never exceeds: declare the typed functions; for streams, call the callback when it happens.
