Filesystem sync · Interface design

How neo-fs sync works

A pure filesystem underneath. A durable local overlay above it. One authority decides the shared tree.

Agreed modelNot implementedInterface design in progress

Read in order for the complete flow, or use the section links. Wide diagrams scroll horizontally on small screens. A, B, C, R and S denote file contents; F and D denote stable entity IDs. Hashes and IDs in examples are abbreviated.

01

One visible filesystem, two local ingredients

Consumers use engine.volume. Its view combines the last installed authority state with ordered pending intent and local timestamps. A local save changes that view immediately after durable local publication.

Accepted locallyPending / private stateConsumer viewAuthority

Pure filesystem responsibilities

Volume handles paths, links and change notification. Store supplies primitives over local node IDs. Neither knows about authority cursors, proposals, conflicts, or tombstones.

Sync responsibilities

The engine owns the overlay, global identity mapping, pending work, transfers and recovery. The authority owns acceptance, semantic rebasing and shared ordering. They are not symmetric peers.

One active engine owns storage, enforced by a lease at .sync/lock; a second opener rejects with LOCKED. The view hides .sync and the authority refuses the name, so neither consumers nor incoming changes can reach it. Direct storage access sees accepted files and that hidden directory, never pending work; importing external edits is a separate integration.

What does the SyncEngine controller expose?

sync() runs one serialized exchange pass; completion does not mean all pending edits were accepted. status() reads the phase (uninitialized, idle, syncing or closed) and unretired edit count. issues() lists errors and preserved versions; neither blocks sync. conflict(id) returns a preserved version; dismiss(id) releases it.

close() finishes local work and releases engine-owned resources while retaining pending changes. It neither waits for server acceptance nor closes the supplied storage. State readers do not require network access.

engine.volume.watch wakes watchers with source local once a write is persisted, and remote for entries whose visible state changed once an installation completes, never during a partial batch.

02

The data: identity, intent and accepted results

A file has a stable identity and a changing state. A path describes where it is now. File bytes are separate immutable objects addressed by their hash.

Replicated state · EntityData
{
	id: "F",
	type: "file",
	parent: "D",
	name: "a.txt",
	mode: 0o644,
	content: hashA
}

A directory has no content hash; a symlink has a target. All share NodeSpec. An accepted Entity adds its revision.

Intent · Operation
{
	type: "update",
	id: "F",
	changes: { content: hashB }
}

The same vocabulary serves local pending edits and authority submissions: create, partial update, or delete. Updates can change location, content, target or mode without replacing untouched fields.

What exactly is hashed, and which metadata is shared?

Revision encoding is SHA-256, lowercase hex, over the UTF-8 JSON encoding of this ordered array:

["neo-fs:entity:1", id, type, parent, name, mode, value]

value is a file's content hash, a symlink's target, or null for a directory. Directory revisions do not hash their descendants. Mode is 0..0o777; symlinks have fixed mode 0o777. Timestamps remain local, and size is derived from contents or the backend. Mode does not model ownership or promise host access enforcement. The local Node still reports mtimeNs and size.

Three levels, not three competing models. An edit journals local intent. A Proposal wraps that intent for submission. A ChangeBatch reports what the authority actually committed.

03

A local save does not overwrite accepted

Start with file F containing A. Saving B through engine.volume.writeFile() stores B's bytes and an edit in private state. Reads then return B even when the network is unavailable.

The edit record

Stores Operation[], before: StoredEntries, and dependsOn: number[]. Before-state captures affected entities, their paths and hashes immediately before this edit—not the whole tree.

The visible result

Reads use pending bytes for changed content and accepted bytes elsewhere. Listings, moves, deletes, links and metadata use the same view. chmod is pending work; utimes is local metadata.

Follow two saves through acceptance

Select a step. This illustrates ordered events, not a running sync implementation. Cursor labels c₀, c₁ and c₂ are readable stand-ins for opaque tokens.

1. The replica is synchronized

Accepted and authority both contain A. No pending operation changes the view.

Dependencies preserve meaning. Edit 2 (B → C) waits for edit 1 (A → B) to be installed before submission. Its base stays B. Pending includes accepted edits whose canonical results have not yet been installed.

04

Submit intent; install the authority's result

The client persists an exact request before sending it. The authority rebases it against current state and accepts all operations or rejects all. The ordered change feed supplies the actual accepted result.

Outgoing · Proposal
{
	id: "m1",
	generation: "e1",
	base: { F: beforeF },
	operations: [{
		type: "update",
		id: "F",
		changes: { content: hashB }
	}]
}

beforeF is complete EntityData with content hash A. Base contains exactly the operated IDs: null for creates, complete before-state for updates/deletes. It is merge input, not a strict whole-entity revision guard.

Incoming · ChangeBatch
{
	cursor: "c1",
	proposalId: "m1",
	changes: [{
		type: "put",
		node: acceptedEntityF
	}]
}

acceptedEntityF includes the full canonical metadata and revision. Deletes are explicit { type: "delete", id } records. These results can differ from the proposal.

Lost response?

Retry the same (generation, id) and identical payload. The server returns the recorded outcome. Changed payload under the same identity is an error.

Rejected?

The shared tree is unchanged. Persist the reason and decision cursor. Catch up to that point or later before capturing the preserved version.

Expired?

An expired generation or history cursor requires bootstrap. Preserve pending work. Do not blindly resend ambiguous old submissions under new IDs.

Even an accepted no-op produces a batch, possibly with no changes. A lost acknowledgment cannot make retry apply the proposal twice. Existing interfaces return conflict, invalid-tree or missing-content for expected rejections; transport, authorization and storage failures reject the call.

05

Rebase filesystem intent by identity

A write targets F, not the string /notes/a.txt. Renaming directory D changes D's name; F still has parent D. This removes much of the complexity that comes from transforming historical paths.

Compare separatelyRule
Content hashWhole-file replacement. Different competing hashes conflict; no text OT or automatic byte merge in v1.
Location(parent, name) is one value. A partial update derives the complete intended pair from its original base.
Symlink targetCompare the stored target, without traversing it.
ModeCompare the whole 0o777 value. Content and mode changes can combine; competing modes conflict.

For each touched component: current = base means apply the proposed value; current = intended means no-op; otherwise, reject the competing values. Independent components can combine.

The authority then validates the complete result: one valid root, directory parents, unique sibling names and no cycles. Removal is a detach: a location update to a null parent, with the subtree untouched. Deletion is a purge of an entity without children. Replacing a name explicitly detaches or moves the known occupant.

Keep the author's base. If entity state B is accepted as M—for example, combined with a remote move—the later B → C edit keeps B as its base. M does not retroactively become the state the author edited. Here B, C and M denote full entity states; v1 rebasing combines fields, not text.

Each entity appears at most once in a proposal; its operation array is an atomic change, not a sequence of intermediate states. Dependent edits remain separate journal records. When a proposal is prepared, consecutive edits to one entity may collapse into one operation with the earliest base, and a connected group of new entities may share one proposal; an edit to a pre-existing entity waits for its prerequisites to be installed. An ancestor rename alone is not a dependency of an ID-based content write.

06

Remote wins; the local version is preserved

F started at A. We saved B; another client committed R. Distinct competing content hashes cannot merge in v1, so the authority rejects our proposal. The client installs R, removes B from the view, and preserves it with its bytes for optional recovery. Nothing waits for a person.

Private · serializable

StoredConflict

{
	id: "k1",
	message: "Competing file contents",
	editIds: [101],
	base:   { F: { path, node: baseF } },
	local:  { F: { path, node: localF } },
	remote: { F: { path, node: remoteF } }
}

Each node is EntityData, including its mode and content hash. Paths are captured for historical meaning. No functions and no embedded file bytes.

Public · hydrated

Conflict

engine.conflict("k1") returns the preserved sides and the operations that lost. Each snapshot offers readFile(EntityId), reading preserved bytes locally.

editIds supplies the operation list; it is not needed to reconstruct snapshot metadata. Known sides cover the same IDs. A null entry means absent; a null base means unknown.

While preservedWhat happens
Incoming authority changesKeep installing and advancing the cursor, including changes to the same entity. The preserved version never changes.
Other outgoing workUnaffected. The losing edit and its dependents left pending together, so nothing waits.
Visible filesystemShows the authority state. Work the authority refused is never visible.
RetentionNo automatic TTL yet; a local retention period is a later knob. Losing .sync loses preserved versions; the authority remains canonical.

Restore

No engine operation. Read the preserved bytes and write them back through the view: a writeFile for lost content, a rename for a lost move. That is ordinary pending work and may lose again.

Dismiss

dismiss(id) releases the preserved version and its retained bytes. Unknown IDs are a no-op. Errors are not dismissed; they clear when the failed operation succeeds.

Capture is one local transition: preserve the version, drop its edits, install the authority state. Snapshot reads require a preserved version and an open engine. Missing/corrupt content and transport/storage errors never cause a capture; they are retried.

Capture before displacement. An incoming deletion or move can invalidate pending work before the server decides our proposal. Preserve its local state in the same transition that installs the change, so the version is captured while its bytes are still at hand.

07

On disk: events, a checkpoint, and shared bytes

The storage root holds the installed tree and clean file bytes. The hidden .sync directory holds enough information to rebuild the overlay, retry requests, preserve lost versions and finish interrupted installations.

/journal/<first>-<last>.json

Immutable segments containing ordered event arrays. New events create new segments; saves do not rewrite one growing JSON file. Sequence ranges are contiguous and never renumbered.

/checkpoint.json

A periodic recovery snapshot through a complete journal segment. Stores accumulated state and still-needed old records, not a second mutable source of truth.

/content/<sha256>

Whole-file bytes for pending writes, incoming installation and retained versions. Identical content shares one file. Clean accepted bytes are not automatically duplicated.

/tmp/<temporary-id>

Unpublished files. Publish bytes or segments by writing, flushing, renaming to their final path, then flushing the affected directories.

Journal eventWhat it remembers
EditOperations, affected before-state and causal dependencies.
Submission / outcomeThe exact immutable Proposal, its edit reference, and the accepted/rejected/bootstrap-required result.
Target / installedIncoming target revisions and content references, retained old state, any displaced local work; then batches of entities whose storage entries match, and on completion new ID bindings and retired edits.
Preserved / dismissedFrozen versions with the edits they capture, and releases.
Local metadata / issueLocal timestamps and actionable errors. Timestamps do not become pending sync operations.

These are responsibilities and field sketches; exact internal event tags and installation records are not yet implemented. Related events can publish in one segment. Bigint metadata is stored as decimal strings.

The two positions must never be confused

What is inside checkpoint.json?

Included old records are retained lookup data, not events to execute again. Startup reads the checkpoint and replays only later segments.

Storage grows with outstanding work, not every clean file. For accepted A and pending B, B lives in state. Before incoming R overwrites A, pin A if a retained base needs it. A conflict can then read A/B/R offline. Snapshot maps duplicate small metadata; file bytes are shared by hash.

Compaction publishes and flushes a replacement checkpoint before removing covered segments. Keep all records and content referenced by pending work, conflicts, uncovered events or recovery. Temporary incoming copies can add space during installation; the design does not require a permanent second copy of every accepted file.

Removal is detachment: one update sets the entity's parent to null, the subtree rides along untouched, and the engine keeps it under .sync/trash until the authority purges it. Deletions come from purges and live in the authority's retained history and the client's journal. Accepted simply removes the entry: no tombstone Node or placeholder file. When authority history is too old to serve a client, require bootstrap instead of keeping every deletion forever.

08

Install safely without a cross-Volume transaction

A server batch is atomic at the authority. Applying it to local files takes multiple writes. The engine records the target in .sync, reconciles storage toward it idempotently, and records installation only after those changes are durable.

Readers see complete local transitions

Serialize view reads and writes with installation so they cannot observe a partial batch. Do not hold that serialization during network waits. Captures never delay cursor advancement.

Recovery is not blind replay

Rerun the reconcile; every step is idempotent, so at most the unrecorded tail repeats. Do not resend requests during local recovery. A later sync() retries persisted identities and resumes exchange.

Interruption or failureRequired behavior
Save interruptedOnly a published, durable edit changes the recovered view. Unpublished temporary content is not an edit. Resolve uncertain publication before assigning more sequences.
Accepted files partially installedKeep the old installed cursor until completion is durable. Rerun the reconcile before serving the Volume.
Final segment corrupt / sequence gapStop for recovery. Do not treat missing state, inaccessible storage or unreadable content as deletions.
Authority outcome unknownRetain the exact request. Retry within its generation; an expired request is settled by comparing the fresh snapshot with the edit, never by automatic duplication.

Core Volume writes need not flush automatically; the engine explicitly publishes durable local saves. Guarantees are bounded by the supplied Volumes' file/directory flush behavior and storage lifetime. No physical append primitive or native tombstone file is required.

09

Opening never touches the network. Bootstrap runs inside sync().

Bootstrap provides a consistent authority snapshot and a place to resume the feed. A fresh replica reaches it through the same sync pass that handles expired history, and reports the gap as a phase rather than hiding it.

Adopted. The signature is synced({ storage, authority }). Opening is local-only; the first sync() bootstraps. Authority.root binds the connection to one tree, and .sync is a protocol-reserved root name.

QuestionDecision
What happens before the first bootstrap?Empty storage opens as an uninitialized replica. Every engine.volume call rejects with UNINITIALIZED; sync() bootstraps, resuming if interrupted. There is one bootstrap path, shared with expired history.
What do pre-existing local files mean?Nothing to the engine. It never touches entries it does not own, so they stay on disk, unsynced and invisible to the view. A migration tool copies files through engine.volume after bootstrap; a host may also route a private Volume at such a directory.
Who pairs accepted and state?Nobody has to. The engine owns one storage Volume: accepted files at the root, private state under hidden .sync, hidden by the view and refused by the authority.
How is the target tree verified?Saved state records the root and an engine-generated replica ID. Opening compares the saved root with Authority.root and rejects a mismatch with TREE_MISMATCH, offline included.

This leaves accepted + pending, shared Operation types, authority rebasing, and conflict retention unchanged. Retention guarantees are in the main design; internal installation algorithms follow during implementation.
