app-code is itself a built-in Frieren app. The project you build inside it is a draft app that runs in a throwaway preview kernel scoped to the project folder — the same kernel + sandbox code that runs shipped apps, just rooted somewhere private. The right-pane Preview is that running app. Install promotes it to /applications; Pack zips it for sharing.

0Decisions locked

From your answers
  • No preview/run split, no pop-out. The right-pane Preview is the live app. There is no second window and no dock icon for a draft — popping out an identical instance buys nothing. The toolbar’s primary button is ⟳ Run / Restart (re-run from clean state); auto-rebuild on save keeps it live in between.
  • Drafts never touch /applications. Each project runs in a scoped preview kernel whose filesystem is rooted at /data/app.code/.devkit/<slug>. Its /applications, /state, /data resolve inside that private scratch folder, so a draft physically cannot overwrite a real app. The instance is dropped when app-code quits; files stay on disk.
  • Source lives in app-code’s data dir — /data/app.code/projects/<slug>/src/… — edited through the volume capability.
  • Ship & share are explicit. Install calls the real kernel.install() (the only write to /applications); Pack emits a downloadable .zip others can import.

1How a Frieren app actually runs

An app is two artifacts produced by kernelHost (packages/app/vite.ts):

  • app.js — headless reducer (defineApp), export const app.
  • gui.js — browser UI (defineGUI), with React kept external and resolved through the page importmap (index.html → /vendor/*.js).

Runtime, end to end:

Two facts make this feature cheap to build:

Already exists

Apps already run in dedicated, isolated workers

worker/kernel.sandbox.ts (workerSandbox) uses the Cloudflare Worker Loader: it spins a dynamic isolate from modules: { 'entry.js': ENTRY, 'app.js': code }, content-addressed by SHA-256 of the code, with globalOutbound: null (no network; capabilities only via ctx). A mirror browser sandbox (src/apps/sandbox.worker.ts, browserSandbox) runs the same bytes for local-first. → The “dedicated worker to run user code” you imagined already exists, sandboxed and cached per code-hash.

The GUI is mounted by a tiny host shim

src/apps/host.ts:179 → mod.gui.mount(stageEl, null, { transport, setMenu }). That is the exact seam to embed a live preview: mount a child app’s gui into a <div> in app-code’s right pane instead of a floating Window.

Install/catalog plumbing exists too: built-ins (app-paint, app-files, app-settings) are listed in vite-appstore.ts BUILTIN_DIRS, cataloged with file hashes, and hydrated into the kernel (src/apps/{catalog,manage,hydrate,seed}.ts).

2Core idea: author draft apps on that same pipeline

Each project is a draft app that runs in its own scoped preview kernel — the same machinery as production, rooted privately inside the project folder:

One live instance, in the pane. app-code dispatches run; the system devkit capability (see §8) compiles the project, news up a preview kernel whose filesystem is rooted privately at /data/app.code/.devkit/<slug>, installs the bundle there, and embeds the running app at a DOM slot in app-code’s own pane. Because that filesystem is private and rooted, the draft’s /applications and /state live inside the scratch folder — the real ones are never touched.

It’s the same kernel.ts and the same browserSandbox as production, so the preview behaves exactly like the shipped app. Drafts stay local-first and never reach the server kernel until you Install. This is the SwiftUI-canvas model: the canvas is the compiled app, not a fake.

4UI / modes — collapse to one

Your instinct is right: no code-mode/agent-mode split, and no in-app chat. Use Frieren’s system agent sidebar (src/shell/AgentSidebar.tsx).

  • Editor view: file tree + editor + an error strip fed by esbuild diagnostics and runtime errors caught at the stage boundary.
  • Preview view: the live mounted draft app (canvas). A “focus” affordance hides the explorer so the canvas goes wide — that’s effectively the old “agent mode” (agent drives, you watch), with no extra plumbing.

One mode, a right-pane [Editor | Preview] toggle, plus a canvas-focus state. The agent is whatever the OS already provides.

5The TS→JS build (your open question)

Recommendation

Use esbuild-wasm, bundling in the browser. Skip Vite-in-browser.

This is the system-provided build chain — it lives inside the devkit capability impl (frieren), not in app-code. The app hands over source files; the system owns the toolchain, the way an OS ships a C compiler. Why esbuild-wasm:

  • It does exactly what kernelHost already does at build time — packages/app/vite.ts bundles app.js with esbuild and builds gui.js with React external. The capability just runs both steps in the browser, once, shared across every dev app it serves.
  • Give esbuild a tiny resolver plugin (onResolve/onLoad) backed by the projects/<slug>/src file map, and:
    • bundle src/app.ts → app.js (ESM),
    • bundle src/gui.ts → gui.js (ESM) with external: ['react','react-dom','react-dom/client','react/jsx-runtime','react/jsx-dev-runtime'] so they resolve through the page importmap to the single shared /vendor React — same instance as host and every other app.
  • Third-party deps (e.g. valibot): pre-bundle a small allowlist, or add an esbuild http-loader to pull from a CDN (esm.sh) and cache in the volume. Start with an allowlist — keeps it hermetic.
  • Compile for one small app is a few ms → recompiling on every debounced save is fine, which is what makes “preview == run” work.
Verdict: Vite-in-browser

Technically possible only via WebContainers (a whole Node-in-WASM, the StackBlitz approach) — heavy, slow cold start, and it buys you a dev server + HMR + npm you don’t need when the kernel already provides module loading, an importmap, and isolation. Park it as a future “full-fidelity” option; don’t build on it.

Lighter still: sucrase/swc-wasm transform-only — but that’s per-file with no resolution, so you’d lean on the importmap for everything. esbuild-wasm’s bundling is worth the ~3 MB wasm for real multi-file projects.

Editor: CodeMirror 6 for v1 (small, fast, good TS highlighting). Move to Monaco when you want real IntelliSense/types (the true Xcode/VS Code feel) — heavier, so make it the deliberate upgrade, not the default.

6The live loop, end to end

  1. Edit a file → app-code writes it to /data/app.code/projects/<slug>/src/… via the volume capability (debounced).
  2. app-code dispatches run; its reducer reads the project source and calls devkit.run({ slug, files }). The devkit capability compiles app.js + gui.js. On error: it returns diagnostics, the last-good canvas stays mounted, the strip shows the errors.
  3. Run in the scoped preview kernel. The capability installs the fresh bundle into a kernel rooted at …/.devkit/<slug> (atomic swap) and re-opens the stage. New code hash → fresh sandbox isolate; the scoped state.json persists across rebuilds → hot-reload feel. ⟳ Run / Restart wipes that state for a clean run.
  4. The capability parents the re-mounted stage at app-code’s [data-preview-slot]. No OS window, no dock entry — the instance lives in the pane, in app-code’s own layout flow.
  5. ⬆ Install = devkit.install → validate + the real kernel.install (check-first guard) → /applications/<id>. Now it’s a normal app (dock, server sync). ⧉ Pack = devkit.pack → zipSync {manifest, app.js, gui.js} → the gui downloads the returned bytes.

7Data model & storage

/data/app.code/
  projects/<slug>/src/                     ← editable source (the real project)
  .devkit/<slug>/                          ← capability-owned scratch; scoped kernel's private world
    applications/preview.<slug>/{manifest,app.js,gui.js}
    state/preview.<slug>.json               ← draft state; wipe to reset (⟳ Restart)
  • Project source: …/projects/<slug>/src/* (+ project meta). Edited via the volume capability — the agent and server can read/edit source directly.
  • Scoped runtime: …/.devkit/<slug>/* is written only by the devkit capability’s scoped kernel — confined to the calling app’s own /data/<appId>, so it can’t collide with real apps. Delete it to fully reset a draft.
  • app-code’s own reducer state stays small/semantic: { openProject, selectedPath, openTabs, rightPane: 'editor'|'preview' }. Transient editor state (cursor, scroll) stays GUI-local per the app state discipline.
  • Shipped app (after Install): the standard /applications/<id> + /state/<id>.json — the only time the real dirs are written.

8What’s genuinely new: one granted capability

app-code is an ordinary sandboxed app — a package with defineApp + defineGUI, shipped and installed through the same machinery as files/settings. No native/sandboxed split, no defineGUI change. Its reducer reads and writes project source through the volume capability, exactly like files. The single privileged thing it does — compile a draft, run it in a scoped kernel, embed that live app in its own window — is one new platform surface: a devkit capability that app-code declares and the host grants.

Why a capability, not a privileged code tier

Privilege in Frieren is graduated through capabilities — the system’s entitlement currency (there’s already an allowlist gate: SYSTEM_SCOPE_ALLOWLIST for files’s system volume scope). The Xcode parallel is exact: Xcode is not the OS; it’s an app that uses the OS app system with extra entitlements. So devkit is just a powerful capability any app may request and a granted few may use — anyone could build a competing app-code by declaring it and being granted it.

What makes it mechanically clean: devkit is a local, main-thread capability — like volume in the browser, it never serializes to the server (invokeClientCapability runs it locally). Its impl is frieren main-thread code, so it natively holds host, createClientKernel, chroot, and the esbuild toolchain. A sandboxed app’s gui.js already runs on the main thread (host.ts mounts it), so the impl reaches into the caller’s own stage (wrapperOf(appId)) and parents the running draft at a DOM slot the gui rendered ([data-preview-slot]). No DOM ever crosses the worker boundary; the reducer only ever exchanges serializable values (file strings, ids, zip bytes).

The whole contract is four serializable methods:

interface DevkitCapability {
  run(i: { slug: string; files: Record<string,string> }): Promise<{ previewId: string; diagnostics: string[] }>
  stop(i: { previewId: string }): Promise<void>
  install(i: { slug: string; files: Record<string,string> }): Promise<{ id: string }>   // → real /applications
  pack(i: { slug: string; files: Record<string,string> }): Promise<{ zip: Uint8Array }>
}

And run’s impl is the composition we verified in code (chroot + createClientKernel + host.open already exist; only the toolchain + wiring are new):

async function run(fs, getToken, appId, { slug, files }) {
  const { app, gui, diagnostics } = await compile(files)          // system toolchain (esbuild-wasm, React external)
  const scoped = chroot(fs, `/data/${appId}/.devkit/${slug}`)    // caller-private, generic
  const kernel = createClientKernel({ fs: scoped, getToken })
  const previewId = `preview.${slug}`
  await kernel.install(appBundleFromMemory({ id: previewId, name: slug, app, gui }))
  host.close(previewId)                                           // restart-safe
  host.open(previewId, { getToken, localKernel: async () => kernel, volume: Promise.resolve(scoped) })
  const slot = host.wrapperOf(appId)?.querySelector('[data-preview-slot]')   // caller’s own stage
  const child = host.wrapperOf(previewId)
  if (slot && child) slot.replaceChildren(child)                  // same document, same thread
  return { previewId, diagnostics }
}

The build chain is system-provided. compile lives inside the capability — esbuild-wasm with a vfs resolver over files, React kept external (resolved through the page importmap, same as kernelHost). The app hands over source; the system owns the toolchain — the “C compiler shipped with the OS,” not bundled by each app.

The sandbox isn’t discarded — it’s used where it belongs. The draft runs in a real browserSandbox via the scoped kernel — our “Simulator.” The tool is unsandboxed-by-grant; the product it builds is sandboxed. Exactly Xcode.

Ship & pack reuse what exists. install = the real kernel.install (what manage.ts does), guarded by a check-first id collision test. pack = zipSync (fflate is already a frieren dep) over {manifest, app.js, gui.js}; import is the existing installZipApp + .zip picker (apps/hooks.ts) — already wired.

9Isolation / security note

devkit is a grant-gated capability: it can run code and write /applications, so it must be granted deliberately (v1: an allowlist constant like SYSTEM_SCOPE_ALLOWLIST; later: a one-time user-consent prompt when an app declares it). It is also browser-local only — there is no DOM or host on the server kernel, so it is simply unavailable server-side. Drafts run in a scoped kernel rooted in a private scratch folder, physically separated from real apps, and never leave the device until you Install — a work-in-progress can’t reach the server or touch /applications. Sandboxing is unchanged: isolates per code-hash with globalOutbound: null, host services only via declared capabilities. The same consent gate covers the later case of importing a stranger’s packed .zip — that code runs with whatever capabilities you grant it, so granting is the moment of trust.

10Suggested build order (minimal first)

The full slice-by-slice plan with code samples lives in PLAN.md. In brief:

  1. Ship app-code as a built-in (add to BUILTIN_DIRS) — the mock launches through the normal pipeline.
  2. Real files, read-only: reducer reads …/projects/<slug>/src via the volume capability; CodeMirror in the editor pane.
  3. Edit + save: debounced write handler through volume.
  4. The devkit capability (the one new platform surface) — contract in the SDK, local browser impl in frieren, grant gate. Verified standalone with a throwaway app before app-code uses it.
  5. Live loop: run/stop through devkit, [Editor|Preview] toggle, persistent [data-preview-slot], error strip, ⟳ Run/Restart.
  6. Ship & share: devkit.install (guarded real kernel.install) + devkit.pack (zipSync); import via the existing installZipApp.
  7. Polish & real consent: replace the allowlist with a grant prompt; canvas-focus, scaffold, diagnostics, Monaco.

11Resolved in code · what’s settled

Resolved (verified against the repo):

  • fs scoping ✅ chroot(fs, root) exists and is the platform’s per-app scoping primitive (volume.capability.ts, frieren.app.ts). No wrapper needed.
  • Offline run ✅ browserSandbox runs each app in a per-(appId, code-hash) module Web Worker, torn down on change — local-first, identical semantics to the server kernel.
  • Embedding the preview ✅ done inside the local devkit capability impl: host.open(id, { localKernel, … }) injects the kernel per open, host.wrapperOf(appId) reaches the caller’s own stage, and the child stage is parented at its [data-preview-slot]. No host.ts or defineGUI change; no DOM crosses the worker boundary.
  • Ship / pack / import ✅ kernel.install ships; fflate is already a dep and bundleFromZip + installZipApp + a .zip file-picker (apps/hooks.ts) already import a packed app. Pack is just zipSync over the compiled bundle.

Settled:

  • Pack artifact → a .zip via the existing fflate (manifest at root), installable through the existing installZipApp path. (Correcting an earlier note — the zip dep and import path are already wired.)
  • app-code privilege → a single grant-gated devkit capability (run/stop/install/pack) in the SDK; app-code stays an ordinary sandboxed app and is the capability’s first consumer. Anyone granted it can build a competing app-code.
  • Scratch & sync → …/.devkit/<slug> under the synced volume (durable, multi-device); a draft backs up as data but never executes server-side until Install (devkit is browser-local only).
