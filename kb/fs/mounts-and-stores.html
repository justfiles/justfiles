Stores, mounts, and where your files actually live

Yes — this is mount(2), not an ignore list. A Store is the flash drive; a binding is the fstab line; the mount row is the mountpoint directory. This page walks the whole thing down to the SQL you can run on your own dev database.

Status. The model below is what packages/fs and packages/core implement and test today. No production database has these tables yet — the running server is still the old twin model (fs_inodes, fs_dirents, fs_sync_nodes). PRs 2–4 of T17 do the swap. Both shapes are shown side by side in §3, using rows from your own .wrangler database.

The short answer to “is this fstab?”

A block device with a filesystem on it A Store — one table of rows, one blob map, one feed yes

fstab is local config; nobody else learns your mounts An announced mount row is replicated: every replica sees the name no — deliberately; §8

The one thing that is not negotiable is that the two trees are two Stores. Isolation is structural, exactly as with a flash drive: the sync engine is handed one store and holds no handle to the other, so no page, tombstone or blob request can name your private data. One table plus a “view” would put a per-row filter on every feed read — that is the ignore-list model this design deleted.

§1 One namespace, two stores

Two rules of the data make the boundary real, with no policy code anywhere:

  • A mount row claims its name like any other row, through the ordinary free guard. So no peer can create a directory called private at the root — the name is taken, everywhere.
  • Only a directory may be a parent. authority.ts’s holdsRows refuses any row whose parent is a mount, so a /private/* row cannot exist in the synced store on any replica, buggy or not.

§2 Where a Store is in the database

A Store is three tables. The default store gets the bare names; a namespaced store gets the same three with a prefix. One Durable Object = one SQLite database = both stores, side by side:

The schema, in full

CREATE TABLE nodes (
  id        TEXT PRIMARY KEY,        -- uuid, minted once, never rebound
  parent    TEXT NOT NULL,           -- root is its own parent
  name      TEXT NOT NULL COLLATE BINARY,
  type      TEXT NOT NULL,           -- 'file' | 'dir' | 'symlink' | 'mount'
  mode      INTEGER NOT NULL,        -- full POSIX mode, S_IFMT bits included
  mtime_ns  TEXT NOT NULL,           -- decimal TEXT: past 2^53, so not INTEGER
  size      TEXT NOT NULL,           -- ditto
  xattrs    TEXT,                    -- one JSON object of base64 values, or NULL
  content   TEXT,                    -- sha-256 hex of the bytes, files only
  link      TEXT,                    -- symlink target, inline
  version   TEXT NOT NULL,           -- '<replica>:<nonce>-<n>' — the author tag is the prefix
  deleted   INTEGER NOT NULL DEFAULT 0,
  seq       INTEGER NOT NULL         -- the one order; the change feed reads this
);
CREATE INDEX nodes_live ON nodes(parent, name, id) WHERE deleted = 0;   -- lookup by name
CREATE INDEX nodes_seq  ON nodes(seq);                                  -- the feed

CREATE TABLE blobs (hash TEXT PRIMARY KEY, data BLOB NOT NULL);
CREATE TABLE meta  (key TEXT PRIMARY KEY, value TEXT NOT NULL);         -- 'lineage'

That is the whole storage model: one table, two lookups, one order, one blob map.

Finding it on your machine

Your local dev DO database is a plain SQLite file:

$ ls apps/frieren/.wrangler/state/v3/do/frieren-Frieren/*.sqlite
b5c2a1a5…6d.sqlite      # one file per DO instance id (= one per user)

$ sqlite3 apps/frieren/.wrangler/state/v3/do/frieren-Frieren/b5c2a1a5…6d.sqlite '.tables'
# today:        fs_inodes  fs_dirents  fs_contents  fs_xattrs  fs_generation …
# after PR 3/4: nodes  blobs  meta  private_nodes  private_blobs  private_meta …
Which store is “/”? The store whose tables have no prefix — nodes. There is no row anywhere that says “this table is the root store”: being the store the volume was constructed over is what makes it the root. storeVolume(A, { bindings }) — A is /, and every binding is a position inside A.

  • id — the file’s shared identity: the sync id where the replica had one, else the old ino. Never re-minted, never rebound.
  • parent — the id of /system/profiles. The dirent table is gone: the name and the parent are columns on the file itself.
  • mode — 33188 = 0o100644: the old 420 = 0o644 plus the S_IFREG bits, so the row states its kind once.
  • content — the same sha-256. The bytes are SELECT data FROM blobs WHERE hash = '6567e4a6…', shared by every row with the same content.
  • version — after migration, migrated:0; after your next edit, <replica-id>:<nonce>-<n>. The prefix is the author, and that is what keeps the push loop from echoing.

The queries, one per path segment

Resolution is literally this — child(parent, name) per segment, which is one index hit on nodes_live:

-- /system
SELECT * FROM nodes WHERE parent = '00000000-0000-0000-0000-000000000000'
  AND deleted = 0 AND name = 'system' ORDER BY id LIMIT 1;
-- /system/profiles
SELECT * FROM nodes WHERE parent = 'b1a1fc40-…' AND deleted = 0 AND name = 'profiles' …;
-- /system/profiles/user.md
SELECT * FROM nodes WHERE parent = '7a8e2395-…' AND deleted = 0 AND name = 'user.md' …;
-- the bytes
SELECT length(data) FROM blobs WHERE hash = '6567e4a6…';

Two shortcuts worth knowing when you go poking:

-- the whole tree of one store, shallow-first (ids abbreviated for reading)
SELECT substr(id,1,8) AS id, substr(parent,1,8) AS parent, name, type, seq
FROM nodes WHERE deleted = 0 ORDER BY seq;

-- what the change feed will hand a replica next, in order
SELECT seq, name, type, deleted, version FROM nodes ORDER BY seq LIMIT 20;

-- this store's identity: every cursor it ever minted starts with this
SELECT value FROM meta WHERE key = 'lineage';

§4 Crossing the mount, query by query

§5 The binding is runtime. Only the name is durable.

The fstab is a JavaScript Map, built when the volume is constructed:

// packages/fs/volume.store.ts
export type Bindings = Map<NodeId, Map<string, Store>>   //  parent id → name → store

const bindings: Bindings = new Map([[ROOT, new Map([['private', localStore]])]])
const vol = storeVolume(syncedStore, { bindings, mintVersion: mint })
ThingWhere it livesSurvives a restart?
The binding (store B goes at this name)memory, in the volume’s closureno — rebuilt at boot
The mount row (this name is reserved)nodes, replicated to every replicayes
The private files themselvesprivate_nodes / private_blobsyes, and they never move

Three consequences, all of them Unix-shaped:

  • An unbound mount row reads as an empty, read-only directory: stat works, readdir is empty, and a write under it is EROFS. That is a device that is not mounted.
  • A binding with no row is a silent mount: nothing is written anywhere, so no peer learns the name even exists.
  • Bindings are only read in the volume’s own store (st === store), so you cannot nest a binding inside a bound store. One level, from the root store.

§6 “I want /private at /mnt/private instead”

Doable, and cheap. What it costs depends only on whether the mount is announced.

The steps, in order

Silent binding (no row): change the key you build the Bindings with. That is the entire operation.

const mnt = (await vol.stat('/mnt')).ino          // the parent's id — bindings key on ids
const bindings = new Map([[mnt, new Map([['private', localStore]])]])
// rebuild the volume; /mnt/private now resolves into the local store

Announced mount (a row exists): unmount, move, remount — the same order mount(8) makes you use:

  1. Unbind (drop the entry / rebuild the volume without it). You must: while it is bound, rename('/private', '/mnt/private') answers EBUSY, because both ends of a rename read their last component straight out of the table and a bound point has no row there to move. Unbind first — exactly “device is busy”.
  2. Move the row. An unbound mount is an ordinary row: await vol.rename('/private', '/mnt/private') — one guarded commit: the row's parent, name and version, plus the mtime of the two directories it moved between. (Or tombstone it and commit a fresh mount row; then the reserved name at the root is released.)
  3. Rebind at (id of /mnt, 'private').
Bindings key on the parent’s id, not on a path string. So if you later rename /mnt → /media, the binding still resolves and your private tree appears at /media/private — it follows the directory’s identity, the way the kernel attaches a vfsmount to a dentry rather than to a string. Nothing to update.
The one thing that is not free: moving a file across the boundary. mv /notes/x.md /private/x.md is EXDEV, and the volume emulates it for a single file (one row into a free name in B, then a tombstone in A — so the file gets a new id and the bytes are re-stored under the same hash in private_blobs). A directory keeps the EXDEV: a subtree is a commit per row across two stores with no guard spanning them, so anything that fails leaves half a tree. That is the price of structural isolation, and it is what a real cross-device mv costs too.

§8 Where it is not Unix

  • No st_dev. Every store spells its root 00000000-…-000000000000, so an id is unique within a store only. A crossed readdir entry reports the bound root’s id, the way a POSIX inode number is unique per device — but there is no device number to pair it with, so nothing may compare two ids without knowing both stores. In practice: never key a cache on an id alone if a mount can be involved.
  • The mountpoint is replicated. An announced mount row syncs, so every replica sees that /private exists and is a mount — that is the point (the name becomes uncollidable), but it does disclose the name. Choose a silent binding when even the existence must stay private; the cost is that a peer’s rows under that name are shadowed rather than refused.
  • An unbound mount is empty, not “the directory underneath”. Unix shows you the mountpoint directory’s own contents when nothing is mounted; here nothing can be underneath, because only a directory may be a parent.
  • Per-replica content is a feature. A synced symlink pointing into a local mount resolves to different bytes on every device — the Unix /etc convention, and the intended shape for .env-style secrets: the tree shape syncs, the content never does.
