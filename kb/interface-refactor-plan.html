architecture @justfiles/agent @justfiles/app wire protocol

Solidifying the platform-agnostic interfaces

A concrete, incremental plan to reshape @justfiles/agent and @justfiles/app from "a bag of reusable pieces" into two coherent products — plus a proposal for a shared UI↔backend wire. The goal: a feature added on one platform lands on every platform by construction.

The thesis

Every recent capability — ask_user, read_doc, error classification, slash-commands, rebuild-on-token-rotate — was added to spud-mac's hand-written copy of the agent orchestration (daemon/agent.ts), because the packages expose primitives (createAgent, text, createAssistant, a dozen create*Tool factories) but not the composition that turns them into a working agent. Each host re-assembles that composition, so the copies drift.

The fix is not more utilities — it is to raise the abstraction one level: expose the composed product (createAgentSession, createAppController) and hide the parts. The test for what belongs on the surface: "is this a concern of the outside world, or an internal ingredient?" A host should declare what it has (a Volume, a backend, an app controller, a doc reader) and receive a working agent — it should never hand-assemble a tool list.

Plan

  1. Reshape @justfiles/agent around createAgentSession — move host-owned orchestration into the package
  2. Migrate both hosts onto createAgentSession — shipped; frieren keeps streaming, loses account tools (temporarily)
  3. Narrow the @justfiles/agent export surface — parts become internal
  4. Capability-provided agent tools — a capability contributes its own tools; re-adds email/calendar generically
  5. Extract createAppController into @justfiles/app — shipped; the one duplicated, platform-true piece
  6. Design a shared UI↔backend wire — proposal + example to think through

A correction, and lessons from pi's AgentSession

Correction — the agent has no "command" concept A slash command is a UI thing. It maps to either a named skill or a plain session method — /new → session.newSession(), /<skill> → session.applySkill(id), anything else → session.prompt(text). So runCommand, commands(), CommandMeta, and CommandResult are gone from the package (they were in the first draft of Step 1). The command registry lives in the host/UI. This is exactly how pi is built.

pi's coding-agent is the same shape as us: a harness over pi-agent-core. Its slash-commands.ts is 40 lines of pure data — a list of { name, description, source: "skill" | "prompt" | "extension" } — and its AgentSession class has no runCommand. It exposes semantic methods (prompt, compact, setModel, newSession…); the interactive mode maps command names onto them. What we take, and what we deliberately leave:

Idea from piHow we apply it (lean)
takeOne AgentSession owns tools + model + compaction + eventsCollapse our two layers (Assistant + per-host orchestration) into one createAgentSession. No wrapper.
takeCommands are UI data with a source; the session has semantic methodsnewSession() / applySkill() / listSkills(); the registry stays host-side.
takeOne narrow event union the UI subscribes toOne SessionEvent = busy/transcript/error (spud-mac's AgentEvent); newSession re-emits an empty transcript. Fixes multi-tab sync too.
takeServices created separately from the session (createAgentSessionServices → createAgentSessionFromServices)Keep our single createAgentSession(ports) for now; adopt the two-phase split only if backend/model resolution grows.
leaveExtension loader, an open tools? escape hatchNo current consumer (spud-mac wires a fixed set) — CLAUDE.md forbids speculative interface. Add a seam only when a second tool needs one.
leave3,100-line AgentSession, ResourceLoader, ModelRegistry, full extension runtime, steering/queue, session tree/forkingOut of scope — these serve a CLI coding tool. Our core stays small; revisit steering/queue only when a real need appears.

The shape it should have

Introduce one entry point. It owns tool wiring, the turn runner, error classification, commands, notifications, and rebuild-on-token-rotate. The host passes what it has; the package decides which tools exist (an app command iff an AppController is given; read_doc iff a readDoc reader is given; the shared email/calendar tools iff account-backed accounts capabilities are given).

packages/agent/session.ts — the product surface (no "command" concept)
export interface AgentSessionOptions {
	volume: Volume
	// static config OR a resolver the session calls each turn — a rotating OAuth token
	// changes `backend.revision`, and the session rebuilds transparently (lossless: the
	// conversation lives on the Volume). Folds in spud-mac's getAgent() cache.
	backend: AgentBackend | (() => Promise<AgentBackend>)  // the `ai` account's credential
	apps?: AppController                    // → the `app` command (how the agent reaches account caps)
	notify?: Channel                        // → turn pings + classified errors, routed
	title?: string                          // notification banner title (host branding)
	readDoc?: (id: string) => Promise<string>  // → read_doc tool + docs prompt block
	timezone?: () => Promise<string> | string
	compaction?: CompactionSettings         // sensible default if omitted
}

export interface AgentSession {
	// ── conversation ──
	prompt(text: string, source?: PromptSource): Promise<string>
	abort(): void
	history(): Promise<readonly SessionEntry[]>
	subscribe(fn: (e: SessionEvent) => void): () => void   // one broad stream — every open UI stays in sync
	// ── semantic actions a UI slash-command maps to (the agent has NO "command" concept) ──
	newSession(): Promise<void>                     // what "/new" calls
	listSkills(): Promise<SkillMeta[]>              // LLM-free — the UI builds its "/" menu from this
	applySkill(id: string): Promise<string>      // what "/<skill-id>" calls (loads body, runs as a turn)
	// ── maintenance (cron) & introspection ──
	runMaintenance(): Promise<void>                   // consolidateMemory
	nextMaintenanceAt(now: Date): Promise<number | null>   // async: resolves the tz first
	systemPrompt(): Promise<string>                   // async: builds lazily on first use
}

// One narrow union (like spud-mac's AgentEvent) — busy/transcript/error — so a second tab
// or the native launcher subscribes once and converges with no polling. `newSession`
// re-emits an empty transcript, which is all a UI needs to reset.
export type SessionEvent =
	| { type: 'busy'; value: boolean }
	| { type: 'transcript'; entries: SessionEntry[] }
	| { type: 'error'; message: string; route?: Route }  // classifyFailure result

export function createAgentSession(o: AgentSessionOptions): AgentSession   // sync: build is lazy (offline-safe)

This replaces today's createAssistant/Assistant — we collapse the old two layers (a bare Assistant plus per-host orchestration) into one product, the way pi's single AgentSession owns tools, model, compaction and events. The word "command" never enters the package: a slash command is UI data that maps to newSession(), applySkill(id), or a plain prompt().

Why this is better
  • One correct assembly, in one place. The tool set, turn runner, and error classification stop being copy-pasted host logic.
  • Capability-driven, not list-driven. A host can't forget to wire ask_user — it's always on; it can't half-wire docs — either it passes a reader or it doesn't. Frieren's gaps become structurally impossible.
  • The token seam is honored end-to-end. backend as a resolver folds spud-mac's revision-keyed rebuild into the product, so frieren gets it the day it adopts OAuth.

Accounts — corrected against spud-mac (the reference; frieren is behind). An account touches the agent in exactly one way: it provides the agent's credential — the ai account, resolved host-side into the backend runtime via resolveAiAccount (that IS the backend resolver, kept). Accounts also enable use-facet capabilities (email/calendar), but spud-mac registers those in its kernel and the agent reaches them through apps (the app command) — there is no email/calendar agent tool, command, or app today (DESIGN.md §8, DAEMON-PARITY). So I reverted my earlier port of frieren's accountTools: no accounts? option, no createAccountTools. That was a frieren-era pattern; folding it into the shared product would impose an architecture spud-mac deliberately dropped. The accounts concept stays first-class — via backend (credential) and apps (capability reach) — just not as a bag of tools. Also dropped the tools? hatch and the session_changed event (no consumer / spud-mac emits an empty transcript instead).
Forward direction — capabilities provide agent tools A consumer-side version already exists: frieren's accounts/agent-tools.ts (the “Agent→capability bridge”, ACCOUNTS-MIGRATION §3.1) hand-writes email/calendar tools that call cap.invoke({ appId:'agent', …, scopes: [] }) — the agent as a trusted capability consumer. But it's bespoke (per-capability, hand-written), app-local (lives in frieren, not a shared package — @justfiles/agent imports no capabilities today), and not in spud-mac. The target generalizes it: a capability contributes its own agent tools, and the session gathers them generically from the capabilities present, so adding a capability extends the agent on every host for free. One layering constraint shapes it: @justfiles/app is pi-free (dep edge is agent → app, never back), so a capability can't export a pi AgentTool. Two realizations: (A) a runtime-neutral tool descriptor (name/description/paramsSchema/execute(invoke, args)) beside each contract + one generic capabilityTools() adapter in @justfiles/agent that binds invoke with the agent's trusted scope; or (B) capability-keyed tool adapters inside @justfiles/agent (they know both AgentTool and the capability types). Either way createAgentSession grows a generic capability-tools seam (roughly capabilities?: Capabilities) — not the bespoke accounts?: {email,calendar} list — coexisting with apps (apps drive stateful mini-apps; capability-tools give direct read/action reach). This is now Step 3.5, where the shapes are spelled out (realization A); Step 2 shipped first, making frieren the concrete consumer that justifies building it.

Capability-provided agent tools

shipped — seam + image; email/calendar descriptors pending generic seam closes the Step 2 regression; spud-mac gains them for the first time — same code

Status: landed with the image capability as first customer (#194): CapabilityTool/ScopedInvoke in capabilities/core.ts, the capabilityTools() adapter in @justfiles/agent, and the single capabilities option on createAgentSession. Two amendments to the shape below proved necessary in practice: execute takes a third { volume } context arg (the image tool offloads bytes to files so base64 never enters model context; passthrough tools ignore it), and a structured { content, details } return splits model-facing text from the out-of-band details channel (a plain return is still JSON-stringified). A third refinement replaced hand-written descriptor lists with derivation from the contract: defineCapability optionally takes per-method MethodMeta (description + input JSON Schema), making the contract self-describing, and implementTool(factory, overrides?) — the tool-side counterpart of implementCapability — derives the tool set from it (passthrough by default; overrides carry only judgment: LLM copy, a friendlier name, a transforming execute). ScopedInvoke<Methods> is typed against the contract, so drift is a compile error. Email/calendar metadata + tool sets and spud-mac wiring remain open; the same MethodMeta is the natural home for seam-level input validation later.

Step 2 dropped frieren's agent-level email/calendar tools. This step brings them back the right way — a capability contributes its own agent tools, and createAgentSession gathers them generically. Add a capability to a host's kernel and its agent tools appear on every host by construction; the agent becomes just another trusted capability consumer (like an app's reducer, but calling tools).

the pattern being replaced — bespoke, per-host, per-capability
// frieren/worker/accounts/agent-tools.ts (deleted in Step 2) — hand-written email+calendar
// tools; spud-mac had NONE. Two hosts, two divergent answers, both owned by the consumer.
accountTools({ email, calendar, getTimezone })  // lives in the host, knows the caps by name
The constraint that dictates the shape @justfiles/app is pi-free — the dependency edge is agent → app, never back (only @justfiles/agent imports AgentTool). So a capability cannot export a pi AgentTool. The fix: the capability ships a runtime-neutral tool descriptor beside its contract, and @justfiles/agent holds the one adapter that turns descriptors into pi tools. This is realization (A) from the Step 1 forward-note; it also future-proofs against ever swapping the agent runtime.
packages/app/capabilities/core.ts — beside defineCapability (no pi types)
// A capability's AGENT-facing surface, described neutrally so it lives in the pi-free app layer.
export interface CapabilityTool<Params = unknown> {
	name: string           // agent-visible, e.g. 'email_list_unread'
	description: string    // when/why to call it (LLM-facing)
	parameters: JSONSchema // input schema — app already carries @standard-schema/spec
	execute(invoke: ScopedInvoke, params: Params): Promise<unknown>
}
// The capability's own invoke, pre-bound to the agent actor + this one capability.
export type ScopedInvoke = (method: string, ...args: unknown[]) => Promise<unknown>

packages/agent/capability-tools.ts — the ONE pi↔capability seam
import type { Capabilities, CapabilityTool } from '@justfiles/app/capabilities'

// Turn a capability's neutral descriptors into pi AgentTools, binding each invoke to the
// AGENT actor. One function — the single place pi-agent-core meets the capability layer.
export function capabilityTools(
	caps: Pick<Capabilities, 'invoke'>,
	entries: { capability: string; tools: CapabilityTool[] }[]
): AgentTool[] {
	return entries.flatMap(({ capability, tools }) =>
		tools.map((t) => toAgentTool(t, (method, ...args) =>
			caps.invoke({ appId: 'agent', capability, method, args, scopes: [] }))))
}
// toAgentTool: wrap { name, description, parameters, execute } into pi's tool object,
// validating params against `parameters` before execute(scopedInvoke, params).
createAgentSession — grows ONE option; both hosts wire it identically
// AgentSessionOptions gains ONE field — NOT accounts?:{email,calendar} (that shape is gone):
capabilities?: {
	invoke: Capabilities['invoke']
	tools: { capability: string; tools: CapabilityTool[] }[]
}
// …build() appends them next to the always-on tools:
const capTools = capabilities ? capabilityTools(capabilities, capabilities.tools) : []
assistant.addTools([bash, createFetchTool(), createSearchTool(), askUser, ...capTools])

// Host wiring — spud-mac gains email/calendar for the FIRST time; frieren gets Step 2's loss
// back; ONE code path feeds both:
createAgentSession({ /* … */ capabilities: {
	invoke: caps.invoke,
	tools: [{ capability: 'email', tools: emailAgentTools },
	        { capability: 'calendar', tools: calendarAgentTools }],
} })
Why this shape Ownership: the email capability owns both its app-facing contract and its agent tools, colocated — one source of truth, no per-host copies. One seam: capabilityTools() is the only place pi meets the capability layer, so the app package stays pi-free. Propagation: the session gathers generically — a new capability (reminders, contacts, files) extends the agent on every host with no session/agent change. Trust: the agent invokes as appId:'agent' with empty scopes — a privileged actor, exactly as frieren's old accountTools did, now generic and audited at the same capability boundary apps use.
One decision left How the session learns which capabilities expose tools: (a) the host passes the list explicitly (shown above — stingy, no magic), or (b) the capability registry carries each capability's CapabilityTool[] and the session auto-discovers (zero host lines, more machinery). Start with (a); promote to (b) only if a third capability makes the per-host line annoying. Also still open: the parameters representation (raw JSON Schema vs @standard-schema/spec vs the agent runtime's typebox) — the adapter owns that conversion, so it's an impl detail, not an interface one.
Breakage & test Additive: a new CapabilityTool type + capabilityTools() adapter + one optional capabilities? option — nothing existing breaks. Unit-test the adapter with a fake Capabilities + one descriptor (assert it invokes with appId:'agent' and returns the result); then wire email/calendar into both hosts and confirm the agent lists unread mail / today's events. This closes the frieren Step 2 regression and gives spud-mac email/calendar reach for the first time — from the same code.
04

Extract createAppController into @justfiles/app

shipped scoped down from a full "AppEngine" to the one duplicated, platform-true piece

The plan here was a broad createAppEngine (kernel + registry + builtins + controller + asset reader + catalog fan-out). Measuring against the two real hosts changed the shape: most of that isn't actually duplicated. Kernel construction is one kernel(…) call; reconcileBuiltins is already a shared package function (only the byte-source differs — packaged fs on spud-mac, an ASSETS fetch on frieren); asset serving and catalog fan-out are genuinely platform-specific (HTTP Responses + cache headers, native .app projection, a Cap'n Web _caps socket). The one thing written twice, near-verbatim, and platform-true is the AppController — and it's exactly what createAgentSession({ apps }) consumes. So per "simplicity first / be very stingy on interfaces", we extract just that, not a speculative mega-engine.

frieren.app.ts + spud-mac/daemon/agent.ts — the same controller written twice
// both hosts hand-wrote this near-verbatim:

	list: async () => (await list()).filter(/* previews */).map(/* id,name,desc */),
	launch: async (id) => { const a = await inspect(id); open(id); return a },
	close, current, inspect, state, run: (id,a,p) => kernel.dispatch(id, {type:a, params:p, actor:'agent'}),
}
packages/app/app-controller.ts → exported from "@justfiles/app"
export interface AppController {
	list(): Promise<AppSummary[]>; launch(id): Promise<AppInspection>; close(id?): Promise<void>
	current(): Promise<AppInspection | undefined>; inspect(id): Promise<AppInspection>
	state(id): Promise<unknown>; run(id, action, params): Promise<unknown>
}
export interface AppControllerPorts {
	windows: { open(id, name): void; close(id, name): void }
	focus?: () => Promise<string | undefined>   // else track last-launched in memory
}
// kernel may be a ready instance OR a lazy accessor (frieren builds it on first use).
export function createAppController(kernel: Kernel | (() => Promise<Kernel>), ports: AppControllerPorts): AppController
both hosts wire only their platform seam
// spud-mac — native windows (open / pkill the materialised bundle):

// frieren — broadcast to tabs + focus from persisted OS state; the accessor also
// arms the caps-socket nudge (ensureSubscribed) before every kernel touch:
createAppController(async () => { ensureSubscribed(); return kernelReady() }, {
	windows: { open: (id) => broadcast({ type: 'app_open', id }), close: (id) => broadcast({ type: 'app_close', id }) },
	focus: currentAppId,
})
Why this is better
  • The controller exists once; the AppController type moves here too (it references ActionMeta, an app type — and @justfiles/app is pi-free, so @justfiles/agent imports it over the existing agent → app edge and re-exports it unchanged, so no consumer breaks).
  • Divergence is captured as honest ports: spud-mac keeps its native open/pkill; frieren keeps its broadcast + OS-state focus. The kernel argument accepts a lazy accessor, so frieren's build-on-first-use + caps-nudge slots in without a bespoke hook.
  • Everything genuinely platform-specific (kernel wiring, builtins source, asset Responses, catalog projection, the Cap'n Web socket) stays in the host — no premature "engine" abstraction wrapped around single-use code.

Design a shared UI↔backend wire proposal — for you to think through

Yes — this is the UI↔backend conversation. Today it's expressed twice and differently: spud-mac uses three Bun WebSocket topics with a typed frame union (daemon/protocol.ts); frieren uses an agent socket with ad-hoc JSON plus a separate Cap'n Web _caps RPC socket. The transport (topics, pub/sub, DO hibernation) is genuinely platform-specific. The vocabulary — what messages mean — is not. So share the vocabulary + a pure router, and let each platform keep its socket plumbing.

The vocabulary (one union), and a pure router

export type ClientFrame =
	| { ch: 'agent';  type: 'prompt'; text: string }
	| { ch: 'agent';  type: 'abort' }
	| { ch: 'agent';  type: 'newSession' }              // "/new" — a semantic action, not a "command"
	| { ch: 'agent';  type: 'applySkill'; id: string }  // "/<skill>"
	| { ch: 'app';    id: string; type: 'dispatch'; rid: string; action: Message }

export type ServerFrame =
	| { ch: 'agent';  type: 'transcript'; entries: SessionEntry[] }
	| { ch: 'agent';  type: 'busy'; value: boolean }
	| { ch: 'agent';  type: 'error'; message: string; route?: Route }
	| { ch: 'system'; type: 'catalog'; apps: AppManifest[] }
	| { ch: 'system'; type: 'skills'; skills: SkillMeta[] }        // the UI's "/" menu source
	| { ch: 'system'; type: 'notification'; notification: Notification }
	| { ch: 'app';    id: string; type: 'state'; state: unknown }
	| { ch: 'app';    id: string; type: 'reply'; rid: string; ok: boolean; value?: unknown; error?: string }

// Pure: no sockets. Maps frames ⇆ the two products. Each platform owns the transport.
export function createHostRouter(deps: { agent: AgentSession; apps: AppController }) {
	return {
		// Push initial snapshots + wire product subscriptions to `send`; returns unsubscribe.
		onOpen(ch: Channel, send: (f: ServerFrame) => void): () => void,
		// Handle one inbound client frame (dispatch, prompt, command…).
		onFrame(frame: ClientFrame, send: (f: ServerFrame) => void): Promise<void>,
	}
}

Why this is better — and what to decide

A single typed vocabulary means the frieren client, the quay WKWebView, and a future mobile webview all speak the same protocol — one UI client library, not one per host. New server→client message? Add a variant; every UI gets it type-checked.

Open questions for you to think through:

  • Where does it live? It references SessionEntry/SkillMeta (agent) and AppManifest/Notification (app), and agent already depends on app. Options: (a) a thin new leaf @justfiles/wire depending on both; (b) fold into @justfiles/agent since it sits at the top; (c) a dedicated @justfiles/host package that also owns createHostRouter and becomes "the backend framework." My lean: (c) long-term, but only once Steps 1–4 prove the products — don't front-run it.
  • One multiplexed socket or three? The ch tag lets you multiplex over one socket (simpler auth, fewer connections — good for mobile) or keep three. The router doesn't care; the adapter decides.
  • Leave _caps out. Frieren's capability proxy is Cap'n Web RPC (bidirectional object references, not flat frames). It should stay its own transport; the router covers only the agent/system/app plain-frame channels.
