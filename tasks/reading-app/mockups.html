Six things worth doing, in order

  1. Select a sentence in an article. Watch selection appear in the state pane, and the Assistant pick it up — with no AI code in the app.
  2. Save the URL that fails. A row appears, but nothing is written to disk. Retry, paste it in by hand, or open the original.
  3. Open dropped-paper.pdf — a loose file someone dropped in /reading. The viewer dispatches on info.doc, so a PDF is just another document.
  4. Mark that PDF read. It has nowhere to record that, so it becomes a folder — lazy adoption, in the disk pane.
  5. Save a working URL. The row is optimistic and the folder appears when the capability returns, seconds later.
  6. Mark one of the articles read. It leaves the list but stays open in front of you. The n read chip is the only way back — and the state pane shows it never left items.

Why the app has no Ask box

The Assistant panel is host chrome — it sits outside the app's border in the window above, and it reads state.current and state.selection like any other agent-visible state. The app declares no ai capability and ships no AI code.

That is the whole reason selection is in the reducer rather than in the GUI. It is the app's only concession to the assistant, and it costs one field and one dispatch on mouseup — a semantic event, not a stream of pointer moves.

The corollary: anything you want the agent to know has to be state. Reading position, the current filter, a highlight — each is a field, or the agent is blind to it.

The shape in three files

Small enough to hold in your head

One capability, one derived index, one watch. The list you see above is the persisted state; the scan is a background reconcile.

capabilities/reader/contract.ts 
// Cloudflare behind it: fetch + Workers AI
// toMarkdown first, then Browser Rendering
// /markdown for SPAs. The app cannot tell
// which tier answered — nor that it is CF.
export interface ReaderCapability {
	read(input: { url: string }): Promise<{
		url: string
		title: string
		markdown: string
		siteName?: string
		byline?: string
		publishedAt?: number
		wordCount: number
	}>
}
info.json — one per item folder 
{
	"title": "The shape of a week",
	"doc": "content.md",        // or "paper.pdf"
	"source": "https://…",     // null when pasted
	"savedAt": 1756345200000,
	"read": false,
	"words": 1740
}
app.ts 
capabilities: {
	volume: volume({ scopes: ['/reading'] }),
	reader: reader({ scopes: [] })
	// no `ai` — the host panel reads state
}

type ReaderState = {
	items: Item[]      // persisted; painted on boot
	current: string | null
	selection: { slug, text } | null
	pending: { url, startedAt }[]   // no file yet
	failed: { url, error }[]        // dismissible
	revision: number
}

// One wake, one reconcile. Coalesced because the
// event carries nothing — it just says "re-scan".
subscriptions: (state, sub) => [
	sub.capability('volume', 'watch',
		{ path: '/', recursive: true })
		.coalesce().to('treeChanged')
]

The reconcile, measured. One recursive scan gives path, type and mtime for the whole subtree; the info.json reads go in a single Promise.all. At 500 items that is ~36ms on disk, and it never blocks a launch — the list is already on screen from persisted state.

Still open

Three calls left, all cheap to reverse

Images: stripped in v1, or written to assets/?

The GUI iframe's CSP blocks remote subresources, so an article's images cannot load from their original URLs — they must be local bytes. Ship text-only. The folder shape means adding assets/ later needs no migration, which is exactly what it is for.

Adopt loose files lazily, or eagerly?

Above it is lazy: a dropped file stays a file until you act on it. Eager is defensible — one shape in the scanner, no branch — at the cost of rearranging files the user just put there. I would take either; lazy is politer, eager is leaner.

Where does the durable cache live?

Cloudflare's cacheTTL caps at 24 hours, so re-saving a URL next month re-renders and re-bills, and two apps saving the same page pay twice. Fine for now — the volumes are tiny. When it matters, a content-addressed cache goes in the host behind the same read(url), and no app changes.

Does read survive a rename?

The slug is the identity, so renaming a folder in Files makes a new item and loses nothing but its read flag — info.json travels with it. Good enough. An id field would fix it properly and is worth one line if it ever bites.
