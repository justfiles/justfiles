Global dialogs

One dialog primitive, two placements. An app-owned decision attaches to its window; a system-owned decision blocks the desktop. The placement is host policy, not a caller option.

Why this exists

An app GUI runs in an opaque-origin iframe without allow-modals, so browser alert() and confirm() are not an app API. The Frieren shell still uses those browser dialogs for uninstall, reset, and install errors. They cannot carry trusted app identity, do not use the design system, and block the browser thread.

One host-owned component fixes both. It renders outside every iframe and stamps who asked — the same trust move notify already makes when it stamps source from the kernel's appId.

Two primitives, one for v1

Dialog · v1

A compact, host-owned message with a constrained action area: alert, boolean confirmation, or a choice of up to three actions. The host owns its chrome, focus, and placement.

Sheet · later

App-owned custom content for forms, pickers, validation, and multi-step work. It will be a separate primitive; this proposal does not define its API.

This follows Apple's boundary: alerts and confirmation dialogs are constrained system presentations, while sheets host richer task-specific interfaces. A dialog has no input fields or custom content; those belong in the future sheet primitive.

API decision — a strongly typed GUI service

A dialog is not app state and not an app capability. app.ts owns the semantic action: delete the note. A human GUI may ask first; an agent or CLI may call the same action directly. The host injects dialog beside the typed app client, only while a GUI is mounted. 

// app.ts — pure app logic, shared by GUI and agent

// gui.tsx — confirmation belongs to the human interface
import { defineReactGUI, type GUIProps } from '@justfiles/app/react'
import type { app } from './app'

function Notes({ client, dialog }: GUIProps<typeof app>) {
	const remove = async (id: string) => {
		const confirmed = await dialog.confirm({
			title: 'Delete “Q3 planning”?',
			body: 'The note and its 4 revisions leave the volume.',
			confirmLabel: 'Delete',
			destructive: true
		})
		if (confirmed) await client.deleteNote({ id })
	}
	// render...
}

export const gui = defineReactGUI<typeof app>(Notes)

GUIProps<typeof app> gives the editor both halves: app-specific action types on client, and the platform-owned dialog contract on dialog. Plain defineGUI gets the same inferred { client, dialog } mount context. 

// @justfiles/app/browser
export interface DialogContent {
	title: string
	body?: string
}

export interface DialogAction<Id extends string = string> {
	id: Id
	label: string
	role?: 'cancel' | 'destructive'
}

export interface ConfirmDialogOptions extends DialogContent {
	confirmLabel: string
	destructive?: boolean
}

export interface DialogClient {
	alert(options: DialogContent): Promise<void>
	confirm(options: ConfirmDialogOptions): Promise<boolean>
	choose<const Actions extends readonly DialogAction[]>(options: DialogContent & {
		actions: Actions
	}): Promise<Actions[number]['id']>
}

export interface GUIContext<A> {
	readonly client: Client<A>
	readonly dialog: DialogClient
}

// @justfiles/app/react
export interface GUIProps<A> extends GUIContext<A> {
	readonly state: GUIState<A> | null
}

The three methods are one constrained dialog primitive with three result shapes: alert() completes, the confirmation prompt confirm() returns a boolean, and choose() returns the exact action-id union. The host supplies standard OK and Cancel labels; the caller names the confirming action and every choice. The editor rejects missing fields, invalid roles, and unknown options without asking each app to restate the contract.

The client is a typed RPC proxy over the GUI's existing MessagePort, not a raw function object crossing the iframe. The host already knows the mounted frame's app and window, so the request has no source, placement, coordinates, icon, or z-index. The host validates one to three choice actions at runtime. Deliberately absent from v1: input fields, custom content, validation hooks, and “don't ask again.”

Placement and lifecycle policy

GUI client

Every app-GUI call attaches to its own mounted window. The host derives identity and placement from the frame; the app cannot name either.

No app window

There is no dialog client to call. Agent and CLI actions continue through the app's semantic API without GUI confirmation.

System caller

The trusted shell calls the coordinator directly and may request the system placement for uninstall, reset, or fatal recovery.

Concurrency

Allow one pending dialog per app and one pending system dialog. Reject overlap in v1; add a queue only when a real caller needs it.

Complete v1 dialog set

These are the only three content shapes. They use the same panel and can appear in either host-chosen placement below; apps choose the semantic operation, never the placement or layout.

The dialog is drawn by the OS on top of the app's iframe, inside the window's own frame — the app can neither move it nor forge one.

Reads as

An alert attached to its owning window. Attribution is structural — it is physically attached to the app that asked, so the label is confirmation, not the only evidence.

Best for

Anything a window owns: delete this note, save before closing, rename, overwrite.

Costs

Needs that app's window. A headless app call cannot fall back to a global blocker, and a dialog behind another window needs the OS to raise its owner.

Reuses

The attached-agent panel already proves host-owned scrim and panel composition inside a window. The dialog gets its own top/titlebar anchor.

Recommended implementation seam

Keep the split sharp: app.ts owns semantic actions; the mounted GUI gets a typed DialogClient; the shell owns one coordinator/component that renders attached dialogs and system alerts.

The GUI bridge sends a typed dialog request over its existing port. The host adapter adds trusted app/window identity and hands it to the coordinator. The shell calls that coordinator directly for system alerts. Queue, focus, Escape, window-close cancellation, and rendering stay out of app code. Agent approval, if it is ever needed for destructive tools, is a separate agent-runtime concern.
