App-Attached Agents

Every app window grows a footer. In its trailing corner sits the agent, in one of two modes: a sheet that rises over the app for a quick question, or a sidebar that opens beside it to work alongside for an hour. The shell chooses the one that fits when you open it. Underneath, a session store that is already generic enough for all of it.

The shape

Two modes with different jobs, and a footer that never moves

The two directions worth keeping are one component and one thread, but they are not the same gesture. Space is the reason: screens are wide and short, and the web has spent fifteen years teaching apps to survive a narrow viewport and nothing at all about surviving a short one. A 500 × 700 app is a layout somebody tested. A 900 × 280 app is a layout nobody has ever seen. So the panel takes width by splitting and takes height by covering.

That asymmetry turns out to be the good news, because it separates two things people actually do. The sheet rises over the app, dims it, and goes away on Esc — for "let me just ask something." The sidebar opens beside the app, changes nothing about it, and stays until you close it — for "let me work on this with you." One is a question; the other is a workbench.

What holds still is the footer: a new strip of window chrome on every app window, with the agent button in its trailing corner. That is the constant affordance in both modes, the way the DevTools toggle stays in the browser toolbar no matter where the panel is parked. It is also the surface that can grow — the place an app's own status line eventually lands.

Decision 01
Height is covered, width is split

The sheet overlays and dims; the sidebar reflows. An app made shorter is an untested layout, an app made narrower is a tested one — so the mode that takes height never takes it from the app, and the mode that takes width is free to.

Decision 02
Selection is never required

The panel is attached to the app, not to a text range. The agent pulls what it needs with app state <id>, which works for every installed app today. v1 needs zero changes to the app SDK.

Decision 03
One character, many rooms

A per-app agent gets its own sessions/ and nothing else — no soul, no avatar. Identity falls back to main, so it is the same face and the same name in every window, remembering a different conversation.

Decision 04
The button is the guaranteed path

Keystrokes inside the app's sandboxed iframe never reach the shell, so ⌘/ works only while the chrome has focus. The footer button is the primary control, not a fallback. One bonus: the sheet's scrim takes focus off the app, so Esc always closes it.

Mode · sheet

Ask, and get back to work

The sheet rises from the bottom of the window body and sits over the app — which keeps its full layout, unmoved, behind a scrim. Nothing reflows, nothing jumps, and the app you return to is pixel-for-pixel the one you left. The dim is deliberate but light: it says the app is recessed, not gone, so the top of the entry stays readable while you type about it.

Because it covers, it should be easy to get rid of: Esc, or a click on the scrim, closes it. It is never restored open — a window you reopen comes back to the app, not to a conversation. The thread is untouched by any of that; only the surface is transient.

Mode · sidebar

Work alongside

The sidebar is a real split: a sibling of the app viewport, taking width the window had to spare. Nothing is covered and nothing is dimmed, because the point is to use both at once — read the app while you type, copy something across, act in the app and come back to say what happened. It stays open until you close it, and it is remembered per window, so an app you always work on with the agent opens ready.

One floor: the app keeps a minimum width. If the window is too narrow to give the sidebar its room without crushing the app, the button opens the sheet instead. The shell chooses from the current geometry, and a cramped split serves nobody.

The new chrome

What the footer is

A 24-pixel strip below the window body, above the bottom border, on app windows only — the conversation window has no app to be about. It follows the existing chrome rules: same --surface as the titlebar, same fade when the window is not focused.

⌃
At rest, focused The face and a chevron pointing where the panel will appear. There is no durable badge or count. A finished turn may put a short-lived notice beside the button while this app window remains open. The leading space stays available for the app's own status line later.
⌄
Open The button takes the accent tint and the chevron reverses. State is per window and remembered, so an app you always talk to opens with the panel already up.
  • It never opens itself. The agent's face may change expression and its footer may show a result, but the panel appears because you pressed something.
  • Notifications stay here. A per-app result lives only in this open window. Closing the app discards it; global notifications never receive it.
  • Esc closes the panel, never the window. Reliable for the sheet (the scrim holds focus); for the sidebar, only while the chrome has focus — see decision 04.
  • The thread is lazy. No session is built when a window opens — only when you first send something. Opening ten apps costs nothing.
  • A reply in flight holds the surface open. The omnibar already works this way; an accidental click must not throw away an answer you are waiting for.
  • Acting is visible. The agent dispatches the app's own actions, so co-presence is free: the window re-renders, and no confirmation dialogue is needed to tell you what happened.
Session data

The store is already generic — one line isn't

This was the part I expected to design and did not have to. The whole transcript layer is already parameterized by an agent id: sessionsDir(agentId), sessionShard(agentId, …), sessionArchive(agentId, …), currentSession(volume, agentId), and a SessionRef that carries agentId as its first field. Per-device sharding, union-by-id merge, and a derived current session (no pointer file to clobber) all come along unchanged.

There is exactly one place where the id is decided, and it is a constant: 

packages/agent/assistant.ts:107
const agentId = 'main'
createAssistant({ agentId = 'main', … })   // a prop, defaulted

So "per-app agents" is a thread-through, not a subsystem. Everything below is the rest of that thread plus the naming convention it needs.

The id scheme

Flat, one path segment, reserved prefixes. An id stays a single directory name, so no code anywhere has to learn that it might contain a slash, and ls /system/agents remains the complete roster. 

/system/agents/
  main/                          the overarching agent — reserved, seeded at boot
    soul.md                      the persona
    avatars/<id>/                the face
    sessions/                    its thread
  app.justfiles.dictionary/
    sessions/                    ← the ONLY thing a per-app agent owns
  app.justfiles.files/
    sessions/
  ws.q3-report/                  later: a workspace room, same shape
    sessions/

App ids are already dotted (justfiles.dictionary), so app.<appId> reads consistently and parses as "first segment is the kind." The alternative — nesting as agents/app/<appId>/ — groups more tidily in the Files app but makes an agent id stop being one path segment, and makes "list every agent" a two-level walk. Not worth it while the roster is small.

Keying on the app rather than the window is deliberate and currently free: the reducer already uses the app id as the window id, and one-window-per-app is "policy, not identity." If a second window per app ever arrives, one thread per app is still the answer you want.

Four rules that keep it from sprawling

  • Maintenance is main's job. scheduleDailyAlarm and memory consolidation must stay pinned to main — ten app threads must not mean ten daily alarms.
  • No per-app persona. A per-app directory holds sessions/ only; soul and avatar resolve to main. If per-room personas ever earn their keep, the directory is already the right place — nothing moves.
  • No per-app tool sandbox. The app thread gets the same app command and a system-prompt line naming its window. It is a thread with a subject, not a permission boundary — that is a much larger design and is explicitly out of scope.
  • The journal question is now due. Doc 05 flagged it: any agent may append to memory/daily/, only main curates core.md. With several agents writing, entries need an agent-id prefix (or per-agent daily files) before this ships.

Shell state

Panel sizes and restored sidebars are shell facts, so they belong in os-state.json beside placements — already synced, already keyed by window id, already tolerant of new fields (the loader validates a handful of keys and normalizes the rest, so an older client ignores what it doesn't know). Placement is chosen from the current geometry each time the panel opens and is not persisted. 

placements: Record<string, WindowRect>
assistant: {
  size: { sheet: number; sidebar: number }  // px, remembered per mode
  open: Record<string, true>         // SIDEBAR only — a sheet is never restored
}

size is two numbers rather than one on purpose: a comfortable sheet height and a comfortable sidebar width are different numbers, and collapsing them means every mode switch hands you a size that feels wrong once. There is no saved mode. open is deliberately sidebar-only — restoring a sheet on boot would put a window back behind a scrim nobody asked for.

Build order

Five steps, each verifiable on its own

1

Key the session

The thread-through above, end to end, with no UI at all. The global agent keeps working because an absent id means main.

Done when two threads run over separate keyed sockets and land in two directories.
2

Add the footer

ds-window-footer in the design package, a footer slot on the Window component, rendered by AppWindow for app windows only. The button toggles the new OS state and nothing else yet.

Done when every app window has a footer that dims with the window, and the flag survives a reload.
3

Raise the sheet

An absolutely positioned panel plus a scrim inside the window body — no layout change to the app at all. The panel is MessagesPanel keyed to app.<appId>, with an app-named header. Esc and scrim-click close.

Done when you can hold a conversation about an app, close the window, reopen it, and the thread is still there — with the app's layout never having moved.
4

Add the sidebar

The real split: data-mode="sidebar" on the body, a draggable seam, a minimum app width with sheet fallback, and the in-header swap control. The shell chooses from current geometry when opening; the header control changes this opening only.

Done when swapping modes moves the panel and changes nothing else — same thread, same scroll position, same draft in the composer.
5

Teach the agent where it is

One line of system prompt naming the attached app, so it reaches for app state before it reaches for anything else. This is the smallest step and the one that decides whether the whole thing feels attached.

Done when "what am I looking at?" is answered without the app being named.

Step 5 is where this succeeds or disappoints.

Steps 1–4 are plumbing and geometry, and they are all straightforward. The thing that makes an attached agent feel attached is whether it reliably orients itself before answering — and that is a prompt and a habit, not a panel. Budget real time for it.

Growth surfaces

Designed for, not built

An app's own status line The footer's leading slot. Word count, sync state, cursor position — the things a status bar has always held. Needs an SDK surface, so not until an app actually wants one.
Pointing at something The optional referent channel: one report({ text, ref }) method beside invoke and subscribe, held in memory, never synced. It makes "what does this mean?" sharper — it is not what makes the panel work.
The third mode Undocked: the panel as its own leashed window, for when the agent needs to show you something big or you want it on a second display. DevTools has exactly this, and mode already has room for the third value.
Per-workspace rooms ws.<id> needs nothing new from the session layer — that is the point of keying it now. The open question is only where its panel lives, since a workspace has no window to attach to.
